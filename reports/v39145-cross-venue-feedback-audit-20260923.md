# v3.9.1.45 이후 피드백: 거래소 공통 경로 원인 점검

## Coinone 공통 실행 조건 적용 — 2026-09-24

2026-09-24 최종 정책 정정 (v3.9.1.46 소스 후보): Coinone 전용 E2E 승인 차단을 제거했습니다. 등록부의 LIVE 허용과 주문 어댑터를 공통 실행 조건에 맞추며, 옛 coinone_live_e2e_verified 값은 사용하지 않습니다. API 인증·명시적 LIVE 시작·회원/주문 범위·위험/최소주문/소유권 조건은 유지합니다. 실제 계좌 검증은 테스터가 진행하며 자동시험 통과를 실계좌 검증 완료로 표시하지 않습니다. 업데이트가 자동 거래를 시작하지 않습니다.

아래 이전 점검의 Coinone LIVE 미지원·승인 전 차단은 변경 전 이력입니다. 위 정책을 현재 기준으로 사용합니다.

### 원인과 이번 수정

- 409 설명/스위치 노출 수정만으로 시작이 열리지 않았던 이유는 등록부 `live_supported=False`와 Coinone 어댑터의 `live_e2e_verified` 검사가 각각 남아 있었기 때문이다. 이는 거래소가 요구하는 E2E 승인이 아니라 앱에 둔 온보딩 제한이었다.
- 등록부를 다른 국내 현물과 같은 LIVE 지원 계약으로 바꾸고 factory의 옛 승인값 전달/어댑터의 검사를 제거했다. 옛 값이 없거나 false/true여도 같은 공통 시작 조건을 적용한다. `account_e2e_verified=False`는 시험 증거 메타데이터로 유지하며 실행 차단에 사용하지 않는다.
- Coinone 시장가 매수 원화 총액·시장가 매도 수량·지정가 매수/매도 수량/가격 및 `post_only=False`를 확인했다. 주문 접수와 체결 완료는 구분하며 조회 실패를 주문 없음으로 바꾸지 않는다.
- Web 기관 카드에서 공개시세 PAPER/학습까지 API 키로 막던 조건을 국내 현물 3곳 공통으로 수정했다. LIVE는 인증 정보가 있어야 시작 요청 가능하며 확인 취소 시 요청은 0건이다. 정지는 키/기관 사용 설정이 사라져도 버튼에서 막지 않는다.
- 1차 전체 회귀 실패 2개는 공개시세 로그도 API 키를 요구해야 한다고 고정한 이전 소스 문자열 검사였다. 공통 공개시세 계약과 브라우저 실행 시험에 맞춰 검사 대상을 수정했다. TypeScript에서 all-true 등록부 타입과 충돌한 비교식 및 계좌 새로고침 분기 실수도 최종 시험 전에 바로잡았다.
- 실제 주문·고객 원본 DB/설정 변경 없음. 이전 실계좌 읽기 조회의 IP 거절은 그대로 기록하며 실계좌 검증 성공으로 대체하지 않는다. 클라이언트 빌드/릴리스는 사용자가 수행한다. 현재 디렉터리에 `.git`이 없어 커밋/푸시하지 않았다.

재현: `scripts/diagnose_v39145_feedback_contracts.py tests -q`, `webui/qa/check-coinone-start.mjs`(로컬 Vite QA fixture, 실제 gateway 미연결). 최종 수치는 `docs/TEST_STATUS.md` 참조.

## 2026-09-24 남은 경로 후속 구현·실계좌 조회 시도

### 코드 변경

1. 부분청산·분할 진입 일괄 청산·위험 기록·증권 실행 품질·주문 명령 갱신을 영속 재처리로 확장했다. 메인 쓰기와 receipt는 한 트랜잭션이고, 완료 후 queue 삭제 전 중단을 재생해 중복 수량/수수료 차감을 막는다. 원래 청산 시각·전략 key/version을 유지한다. 늦은 불확실 주문 명령이 확인 상태를 지우지 않는다. PAPER-only 재처리가 LIVE 손익을 막지 않도록 주문 소유권을 대조한다.
2. 진입 수수료가 없는 신규 기록/부분청산을 0원으로 인증하지 않는다. 분할 진입 일괄 청산의 추정값은 `pending_exchange_reconciliation`으로 남긴다. 기존 `cleanup_old_logs`의 거래/위험 원장 삭제를 제거했다. 신규 진입 공통 경계는 디스크 가용 공간 64MiB 미만/조회 실패를 보류하며 보호·청산 호출은 제외한다. 갑작스러운 디스크 전체 고갈이나 물리 장애의 기록 무손실 보장은 아니다.
3. 증권 `get_recovery_order_fills`와 복구기를 연결했다. 진입·청산 양쪽 ID/종목/수량/실체결가/명시 비용으로만 정산한다. KIS/키움 날짜별 경로, 신한/미래에셋 계약 프로필 기반 경로를 추가했다. 주문가 폴백, 불완전 연속조회, 없는 수수료·매도세금의 0 대체를 거절한다. 주문 번호가 없는 과거 lot 자동 귀속·연속조회 완결·공급자별 비용 자료 확보는 아직 남았다. 모든 증권사 과거 원장 복구 완료라고 표시하지 않는다.
4. Coinone 부분체결/부분취소·client ID·수수료 누락·조회 실패 상태와 native 과거 체결 페이지를 보강했다. 100건 페이지를 이어 읽으며 최대 20페이지 뒤에도 미완료면 성공으로 반환하지 않는다. [주문 조회 규격](https://docs.coinone.co.kr/reference/order-detail), [체결 조회 규격](https://docs.coinone.co.kr/reference/find-completed-orders), [미체결 조회 규격](https://docs.coinone.co.kr/reference/find-active-orders)을 대조했다. 코드 시험과 실제 주문 E2E는 별개다.
5. 전략 입력에 여러 파일·로컬 폴더와 CSV/TSV/XLSX/DOCX를 추가했다. 40개·24MiB/개·64MiB 합계, 통합 본문 60,000자, 자료별 해시/중복/추출/포함/축약 기록. XML 외부 선언·과대 압축을 거절하고 매크로/수식을 실행하지 않는다. 서로 다른 실행 규칙은 임의 결합하지 않고 사용자 확인을 요구한다. Drive URL의 폴더 전체 자동 탐색·구형 XLS/DOC는 미지원이다. 이미지/영상별 추출에 기존 AI 비용이 발생할 수 있다.

### v3.9.1.46 국내 현물 잔여 자산 위험 평가 수정

#### 확인된 원인

제보 알림의 발생 지점은 코인 선정이 아니라 `RiskManager._get_live_equity_snapshot`이다. 잔고 전체를 `asset/KRW`로 평가하면서 `ExchangeManager.get_current_price`의 0 반환을 모두 가격 실패로 처리했다. 이 float API는 미지원 마켓과 일시적 오류를 구분하지 않는다. KRW 직거래가 없는 자산, 지원 마켓 없는 과거 잔고, API 실패를 한 종류로 묶어 계좌 전체 신규 진입을 보류했다.

### v45 수정과 이번 수정의 차이 / 이전 완료 판단 정정

v45가 고친 것은 국면 계산 입력(누락 거래량·평탄 RSI·증권 비정상 표본), PAPER/LIVE/학습 수신 필터, 같은 국면 중복 제외, 전송 응답 오류·채널 예외 격리다. v46에서 확인한 핵심은 그 앞단의 서비스/브리지가 전역 PAPER OFF를 LIVE로 해석해 LEARNING/기관별 PAPER 시작까지 LIVE 게이트로 막는 결함이다. 따라서 감지→발행 함수 시험이 통과해도 사용자 앱에서는 그 함수까지 도달하지 못할 수 있었다. 기관별 정식 모드 판정을 시작 경계에서도 사용하도록 고쳤다. 이는 확정된 소스 결함이지만 고객의 Binance 미수신 전체를 설명한다고 단정하지 않는다. 이미 실행 중인 LIVE 기관의 미수신에는 후보·시세·확정 전환·필터·전송 상태를 별도로 대조해야 한다.

### A04 — unknown/REAL 로그의 의미

- Coinone 연결 문구는 `connect()`에서 시장 목록 로드 후 출력된다. 분석 성공/실패/실행 중임을 의미하지 않는다.
- Binance CCXT 어댑터 포함 암호화폐 어댑터 7개 `self.log_event` 래퍼가 공통 logger에 `execution_mode`를 넘기지 않는다. 기본값 `unknown`이 표시된다.
- `UnifiedTrader.execute_trading_cycle_unified`는 PAPER/DEMO 외에 LEARNING도 REAL 문자열로 출력한다.
- 연결 이벤트에 종목·전략·주문이 없는 것은 정상일 수 있다. ‘해당 없음’과 ‘필수 근거 누락’을 구분하고 추정값으로 채우지 않아야 한다.
- 증권 어댑터 4개는 `_noah_execution_mode`를 전달하는 별도 코드가 있다. 초기값 unknown이며 실제 서비스 문맥 주입 전 연결 이벤트는 별도 확인이 필요하다. 코인과 같은 래퍼 누락이라고 단정하지 않는다.

### A05 — 전략 귀속 저장 계약 단절

- `TradeLog`, 실 `trade_log` 테이블, `Recorder.log_trade_entry`, Binance `_log_trade_entry`에는 전략 key/version 저장 경로가 없다. `model_version/strategy_variant`는 전략 버전 식별자 대체물이 아니다.
- 포지션에는 custom strategy key/version이 있지만 원장으로 넘어갈 때 유실된다.
- 실 Recorder가 만든 임시 DB에 알려진 전략 진입을 기록한 뒤 읽으면 7기관 모두 key/version이 빈 값이다. 모의 확정 순손익 0.9는 보존된다. **전략 귀속 누락과 계좌 PnL 누락은 별개다.**
- `StockAnalysisService`의 BUY 및 부분청산도 같은 `TradeLog` 모델을 쓴다. 증권·ETF도 저장 계약 보강 범위지만 증권 실계좌 체결을 수행한 것은 아니다.
- `SourceTradeHistory`는 기본 전략/수동/레거시 미확정/커스텀 유실을 모두 같은 ‘전략 귀속 미기록’으로 보여준다.
- 기존 `tests/test_source_trade_history.py`는 생산 DB에 없는 전략 컬럼을 수동으로 만든다. 읽기 시험은 통과하나 실제 쓰기→읽기 연결은 검증하지 못한다.

### A06~A08 — 보호주문: 최우선 수정 범위

- Binance `trader.py:4675`는 일반+Algo를 조회하지만 `:5049`는 일반 주문만 확인한다. Algo TP·SL이 있는 모의 상황에서 최종 경고를 재현했고 Algo 조회 호출은 0회였다.
- `TpSlManager`에는 통합 조회가 있지만 이 마지막 경로는 사용하지 않는다. 기존 통합 조회 단위시험 성공으로 실제 호출부를 보증할 수 없다.
- 공통 선물 `_verify_and_repair_tp_sl`은 OKX의 `tdMode`만 있는 일반 지정가, Bybit/Bitget의 값이 빈 TP/SL 필드만 있는 주문도 보호주문으로 간주한다. STOP 한쪽만 있어도 TP/SL 점검을 종료한다.
- 같은 메서드에서 조회 예외를 발생시키면 빈 목록으로 바꿔 **가짜 보호주문 재발주 함수를 호출**한다. 실제 주문은 전혀 제출하지 않았다. 3기관 × 3경우 = **9개 조합** 재현.
- Binance `get_open_algo_orders`, 공통 선물 어댑터 `get_open_orders`도 오류와 정상 빈 결과를 같은 `[]`로 반환한다.
- 공통 선물 어댑터는 현재 일반 `fetch_open_orders` 호출을 사용한다. 설치 CCXT 버전과 기관별 조건부/attached 주문 API의 실제 반환 범위는 추가 검증이 필요하다. 다른 기관에 Binance API를 그대로 적용하면 안 된다.
- 국내 현물은 선물 보호주문 메서드에서 제외된다. ‘현물 보호가 모두 정상’이라는 결론은 아니다. 증권/현물의 클라이언트 청산·실행 종료 시 보호 정책은 별도 시험해야 한다.
- 보호 상태는 `TP 확인 / SL 확인 / 일부 누락 / 조회 실패 / 체결·취소·종료`를 구별하고, 주문 ID·방향·소유·포지션·유효 가격/수량으로 판정해야 한다. 조회 실패를 근거로 중복 주문을 만들거나 확인 완료로 표시하면 안 된다.
