### 이번에 추가로 발견·수정한 결함

실제 로그에 `name 'inserted_id' is not defined` 오류가 중복 로그를 제거한 고유 줄 기준 289개 있었다. 현행 소스에도 같은 결함이 남아 있어 고객 DB의 기존 통계값으로 복사본에서 재현했다.

`save_exchange_trade_stats`는 INSERT와 commit을 완료한 **뒤** 정의되지 않은 `inserted_id`를 반환하여 예외 처리에서 `False`를 반환했다. 따라서 이는 “통계 저장 성공 후 실패 오보고”이며 40건의 청산 근거 누락과 별개다. 이것이 거래 행을 삭제했다거나 40건 누락의 단독 원인이라고 해석하지 않는다.

INSERT 직후 `cursor.lastrowid`를 보존하도록 수정했다. 동일 고객 통계값 재실행에서 정상 ID 반환, 오류 로그 없음, 거래 원장 무변경을 확인했다. 11개 기관 × 현재/이전 통계 스키마 22개 회귀시험을 추가해 양수·음수 갱신과 거래 원장 보존을 검사했다.

**판정: 유지관리 작업과 근거 없는 확정/우회 방지는 동작하지만, 이 고객이 복구 후 거래를 재개하는 최종 인수 조건은 실패다. 배포 보류를 유지한다.**

## 후속 구현: 청산 ID 없는 과거 원장의 API 복구

위의 “고객이 반복 점검해도 복구되지 않는다”는 문제를 해결하기 위해 `BinanceHistoryRecovery`를 추가했다. 기존 로컬 ID가 없으면 API 조회 없이 끝나던 동작은 더 이상 native Binance 복구 경로의 기본 동작이 아니다.

### 실제 구현

- 서명된 읽기 API로 종목·기간별 userTrades/allOrders/allAlgoOrders/income를 수집한다. 6일 이하 구간, 1000건 포화 시 시간 이분할, 영속 체크포인트와 구간 연속성 검증을 사용한다. fromId와 날짜를 함께 보내지 않는다.
- 현재 포지션 수량·positionSide·updateTime을 수집 전후 대조하고, 전체 체결을 역산해 알려진 진입 주문 직전의 flat과 최종 flat을 증명한다. 이후 별개의 수동 거래가 있어도 과거 독립 구간은 재구성할 수 있다. 같은 구간에서 추가 진입/기존 보유분이 섞이면 추정 배분하지 않는다.
- 진입·청산 주문의 전체 체결 수량과 FILLED 상태, 실현손익과 정산 income의 tradeId, 실제 수수료 통화를 대조한다. 순손익은 실제 실현손익 - 진입 비용 - 청산 비용이다. 펀딩·이체를 전략 수익으로 섞거나 차액을 특정 거래에 억지 배분하지 않는다.
- 여러 청산 주문도 모든 실제 fill의 귀속을 원자적으로 저장한다. 단일 주문 ID가 없을 때 가짜 ID를 만들지 않는다. 기존 실행 원장 저장 검증이 실패하면 trade_log를 확정하지 않는다.
- 조회 중 포지션 변화/키 교체, 보존기간 초과, 혼합 귀속, 지연 정산, 잘못된 비용, 같은 1ms 조회 포화는 사유를 남긴다. API 오류를 빈 원장으로 취급하지 않는다.
- 같은 작업의 중단/재시작은 완료 페이지를 재사용한다. 명시적 새 점검은 미도착 자료도 다시 조회한다. 운영 기본값에서 원장 페이지 간 최소1.5초 여유를 두고 요청 예산을 유지한다. 상태 화면이 열려 있으면 예산 후 자동 이어하기를 수행한다.

### 새 시험 38개

1/40/301건 전체 복구, 600거래(1200 fills)의 포화 구간 분할, 첫 +0.25와 다음 +0.02의 gross 합계 +0.27 보존 및 비용 차감, 음수 손익, 롱/숏·hedge, 진입/청산 분할체결, 여러 청산 주문, 별도 수동 거래 혼재, 혼합 진입 거부, API 실패 후 재시도, 지연 income 재조회, 계정 키 변경, 원장 저장 실패, 귀속 충돌, commit 후 checkpoint 전 충돌/재시작을 검사했다.

ExchangeManager의 native client/adapter wrapper 두 경로, NaN/무한대/수치 범위 오류, 복구된 UTC와 기존 offset 시각의 실제 시간순 정렬도 확인했다. 거래 통계의 기존 `exchange_realized_pnl` 계약을 유지해 첫 1건과 2건의 gross/net 합계가 DB뿐 아니라 `AccountQueryService.trading_statistics`에도 표시되는지 검사했다.

**이 시험의 거래소 응답은 계약 fixture이며 해당 고객의 실제 API 원장이 아니다.**

### 고객 데이터 재검증

동일한 원본 SHA256과 보조 파일 해시를 보존했다. 복사본의 실제 미대조 40건을 새 resolver에 넣어 **40/40건, 14개 종목이 native 과거 복구의 provider 조회 경계에 도달함**을 확인했다. 이 검사는 조회 시작 지점에서 명시적으로 중단한다. 가짜 포지션/체결/PnL을 고객 기록에 넣지 않았고 실제 provider 호출은 0회다.

기존 저장 원장만으로 재실행한 결과는 여전히 부분 비용 보완94/확정 손익0이다. 이 수치는 거래소 API에 없는 자료를 확인했다는 뜻이 아니라, 공유된 오프라인 자료만 사용한 결과다. 실제 API 응답을 받는 클라이언트 실행이 남은 계정별 확인 단계다. 개발자가 각 회원의 DB를 받아 수동 보정하도록 설계한 기능이 아니다.

검증 스크립트의 작업 복사본 조회는 SQLite `mode=ro`로 WAL을 포함해 읽도록 수정했다. 변경 가능한 복사본에 `immutable=1`을 사용하면 WAL의 commit을 놓쳐 반복 실행 결과를 잘못 비교할 수 있었다. 원본은 여전히 SQLite로 열지 않고 파일 복사/해시만 한다. 수정 후 반복 실행에서도 거래 원장·체결 건수 무변경을 확인했다.

### 빌드·화면

Node22.23.1 웹 빌드 통과(72 modules, 기존 대형 chunk 경고). `recovery.html?discovery=1` 격리 화면에서 한 번 실행 → 60구간 수집/4대기 → 자동 이어하기 → 64구간 완료를 Chrome으로 확인했다. 한국어/영어 진행·완료·안전 문구를 확인했다. 화면의 40/40 완료는 UI fixture다. **사용자 실제 40건 복구 완료 화면이 아니다.**

공개42 manifest는 변경하지 않았다. Windows 설치기·실기관 계정 검증·배포는 수행하지 않았다. 다른 기관의 청산 ID 없는 historical adapter 및 혼합 귀속하의 별도 재개 정책은 이번 Binance 구현으로 완료됐다고 간주하지 않는다.

## 고객 전체 DB를 사용한 복구 통합시험 추가

사용자 요청에 따라 provider 경계에 도달하는지만 보는 검사에서 더 나아가, **고객 DB 전체 사본을 유지한 채 실제 복구 worker → native BinanceClient 읽기 메서드 → 체결/거래 저장 → 거래통계 조회 → 기존 수익성 정책**을 실행했다. 다른 고객 기록을 삭제하거나 40건짜리 단순 DB로 바꾸지 않았다.

```sh
.venv/bin/python scripts/verify_customer_history_pipeline.py \
  'data/test logs/trading.db' --as-of '2026-09-20T12:30:00'
```

### 실제 자료와 시험 입력 구분

- 실제 고객 자료: 원본 DB 전체, 문제의 40개 행 ID·종목·진입 주문 ID·방향·수량·진입 시각, 주변 거래·기존 실행 원장. 40건의 진입 주문 소유 행은 모두 유일했다.
- **시험용 입력**: 누락된 API 응답. 가상 청산 주문/체결 ID·청산 시각·가격·손익·수수료·포지션 스냅샷을 명시적으로 공급했다. 각 청산은 시험상 진입 10초 후이고 거래당 수수료는 0.003 USDT다. 이것을 고객의 실제 청산 시각/손익이라고 해석하지 않는다.
- 고객 키·네트워크·거래 엔진을 사용하지 않는다. 네트워크 socket 연결은 테스트 중 예외 처리되며, 실제 native 읽기 메서드 아래의 전송 계층만 로컬 응답으로 대체했다. 허용되지 않은 경로는 실패한다.
- 첫 2건 시나리오는 미확정 AVA 두 행에 +0.25/+0.02를 공급한 회귀시험이다. 스크린샷의 두 거래에 대한 실제 API를 재생한 것이 아니다.

세 시나리오 모두 **대상이 아닌 거래 행·PAPER·미청산 행은 무변경**, trade_log 행 추가/삭제 없음, SQLite quick_check=ok, 자동 거래 시작/재개 없음. 45일 전체 유지관리 대상은 1,174건이므로 40건에만 시험 응답을 공급한 시나리오의 남은 대상은 1,134건이다. 이것을 최근 300건의 차단 건수와 혼동하지 않는다.

기존 18개 모듈도 다시 실행하여 **413 passed, 기존 deprecation warning 1개**를 확인했다. 실제 저장 원장만 재생하는 별도 스크립트 결과는 비용 부분 보완 94건 / 확정 손익 0건으로 동일했다. 원본 DB·WAL·SHM 해시 전후 동일.

**판정:** 고객 DB 구조에서 자동 복구·저장·통계 합산·차단 사유 재평가·재시도까지 통합시험을 통과했다. 이 범위에서 추가 실패는 발견되지 않았다. “실제 API 자료가 없으니 DB로 더 시험할 수 없다”는 것은 맞지 않는다. 동시에 시험 입력으로 통과한 40건을 고객 계좌의 실제 정산 복구 완료로 보고하지 않는다. 이번 추가 작업은 검증 도구·증거 문서 보강이며 운영 코드의 추가 변경이나 배포는 하지 않았다.
