# 문서 관리 정책

## 📋 기본 원칙

### 1. 기존 문서 우선 사용
- **새로운 MD 파일 생성 금지**: 질문이나 답변은 기존 문서에 추가/업데이트
- **중복 문서 생성 금지**: 비슷한 내용의 문서가 이미 있으면 기존 문서에 통합
- **임시 문서 금지**: TEMP, TMP, 임시 등의 이름으로 문서 생성 금지
- **승인된 예외**: 반복 실행해야 하는 공식 QA 런북은 사용자 요청과 보안 검토가 있을 때 한 기능 영역당 1개만 둘 수 있다. 실제 비밀번호·API 키는 기록하지 않고 비밀관리자 항목명만 적는다.

### 2. 문서 통합 및 정리
- **주요 문서에 통합**: 
  - `TRADING_FLOW.md`: 거래 플로우 관련 모든 내용
  - `UPDATE_PLAN.md`: 개선 계획 및 진행 상황
  - `CHANGELOG.md`: 버전별 변경 사항
  - `USER_GUIDE.md`: 사용자 가이드
  - UI 플랫폼 전환: `ARCHITECTURE.md`(목표 구조·불변 계약), `UPDATE_PLAN.md`(단계·백업·롤백), `UI_DESIGN_GUIDE.md`(화면 기준), `TEST_STATUS.md`(검증 경계)에만 나누어 기록하고 별도 중복 계획서를 만들지 않음
- **중복 문서 정리**: 완료되거나 사용하지 않는 문서는 삭제 또는 아카이브

### 3. 문서 업데이트 규칙
- **질문 답변**: 관련 기존 문서에 섹션 추가
- **버그 수정**: `CHANGELOG.md`에 추가
- **계획 변경**: `UPDATE_PLAN.md`에 업데이트
- **사용자 가이드**: `USER_GUIDE.md`에 추가
- **인앱 사용자 메뉴얼**: `ui/widgets/user_manual_widget.py` — 제품 방향·책임 경계·기능 설명을 `ARCHITECTURE.md`·`CHANGELOG`와 어긋나지 않게 유지 (아래 정합성 계층 참고)
- **인앱 FAQ 데이터**: `data/nwsoft/user_manual_data.json` — 사용자 질문/용어/주의사항은 `USER_GUIDE.md`·인앱 메뉴얼과 함께 동기화

#### 3-1. 버전 표기 강제 규칙 (중요)
- 배포 버전(`vX.Y.Z`)은 **실제 릴리스/배포 승인 기준**으로만 올린다.
- 문서 동기화/표현 정정/운영 기준 보강만으로는 버전을 올리지 않는다.
- 문서만 바뀐 경우 표기 형식은 아래를 사용한다.
  - `YYYY-MM-DD - 문서 동기화 (배포 버전 변경 없음)`
- 버전 상향 권한 기준:
  1. 인앱 버전 표기 변경
  2. 빌드 산출물 배포 버전 확정
  3. CHANGELOG/USER_GUIDE/인앱 메뉴얼 동시 반영
  위 3개가 충족되지 않으면 버전 번호를 변경하지 않는다.

#### 3-2. 날짜 표기 규칙
- 날짜는 문서 히스토리와 기준일 명확화를 위해 사용한다.
- 기본 형식: `YYYY-MM-DD`
- 허용 위치:
  - CHANGELOG 항목 헤더
  - "기준선"/"검증일"/"상태 점검일" 표기
- 금지:
  - 근거 없는 미래 일정 단정
  - 문서마다 다른 날짜 형식 혼용

### 4. 타임라인 기록 규칙
- **과장된 주 단위 일정 금지**: 현재 사이클처럼 AI 자동화와 병행해 빠르게 진행하는 경우, 근거 없는 `2주`, `한 달`, `분기` 표현을 기본값으로 쓰지 않음
- **기본 단위는 D0/D1 스프린트**: 오늘 끝낼 일은 `D0`, 내일까지 끝낼 일은 `D1`로 기록
- **48시간 초과 항목은 분리**: 48시간 안에 닫히지 않는 항목은 `후속 스프린트`로 명시하고 이번 완료 항목과 섞지 않음
- **배포 기준은 시간보다 상태**: `실행 가능 경로 확보`, `회귀 테스트 통과`, `문서 동기화 완료`를 배포 기준으로 기록

## 🔗 문서 정합성 계층 (일괄 개발 기준)

여러 문서가 같은 사실을 다르게 말하면 개발·대외 설명이 갈라집니다. **아래 순서가 높을수록 “정본에 가깝다”**고 보면 됩니다.

| 우선순위 | 자료 | 용도 |
|---------|------|------|
| 1 | **실제 코드** (`main.py`, `trading/`, `api/`, `ui/`) | 동작·경로·플래그의 최종 증거 |
| 2 | **`CHANGELOG.md`** | 버전별로 무엇이 바뀌었는지 |
| 3 | **`ARCHITECTURE.md`**, **`TRADING_FLOW.md`** | 모듈 책임·거래소 라우팅·금지 사항 |
| 4 | **`docs/README.md`**, **`DEV_GUIDE.md`**, **`AI_API_ARCHITECTURE.md`** | 개발 온보딩·API 연동 |
| 5 | **인앱 메뉴얼** (`user_manual_widget.py`) | 최종 사용자용 요약(법적 고지·UX 톤) |
| 6 | **`USER_GUIDE.md`** | 사용자/개발 공용 상세 가이드(코드 기준으로 최신화 필요) |
| 7 | **`NOAHAI_TECHNICAL_WHITEPAPER.md`** | 기술 스토리·개념 모델(코드와 1:1이 아닐 수 있음) |
| 8 | **`BUSINESS_PROPOSAL_2026.md`** 등 사업·R&D 기획 | **제출·로드맵·비전** 중심. “이미 전부 구현”으로 읽지 말 것 |

### `BUSINESS_PROPOSAL_2026.md`와 코드의 관계

- 문서 성격상 **정부 R&D·사업기획**에 맞춘 **확장 목표·실증 서술**이 포함됩니다.
- **6개 거래소**, **AlphaArena**, **증권 확장** 등은 방향과 실증 축으로는 맞출 수 있으나, **문장 단위가 곧바로 현재 빌드의 ON/OFF 기능을 의미하지는 않습니다.**
- 불일치가 보이면 **코드(1) → CHANGELOG(2) → ARCHITECTURE(3)** 를 먼저 고치고, 기획서·화이트페이퍼·메뉴얼은 뒤따라 맞춥니다.

### 버전·제품 문구를 올릴 때 동기화 체크리스트

1. `CHANGELOG.md`에 동일 버전 항목 추가 여부  
2. `ARCHITECTURE.md` 상단 버전 문구(또는 “메뉴얼/CHANGELOG가 더 최신일 수 있음” 주석)  
3. `user_manual_widget.py` 창 제목·본문에 버전·날짜  
4. `USER_GUIDE.md` 제목 버전(선택)  
5. **책임·실행 연계** 표현: `ARCHITECTURE` 책임 경계 ↔ 인앱 「📚 소개」「⚖️ 이용 안내」 ↔ `USER_GUIDE` 서술이 같은 말을 하는지

### 인앱 메뉴얼(`user_manual_widget.py`)과 톤·사실 정합 (2026-04 기준)

다른 MD를 쓸 때 아래는 **인앱 메뉴얼과 같은 말**을 쓰도록 맞춥니다(과장·구버전 방지).

| 주제 | 정합 규칙 |
|------|-----------|
| **탭 이름·순서** | 작동 원리 탭은 `🤖 NoahAI 작동 원리` 표기. 탭 개수·순서는 **코드의 `create_*_tab` 호출 순**이 정본(역사적 문서의 “6개 탭” 등은 참고만). |
| **📅 vs 📡** | `📅 업데이트` = 버전별 변경 요약. `📡 플랫폼 방향 및 업데이트` = 비전·로드맵·철학(일정 약속 아님). |
| **환류·학습** | 자동 루프(성과 기반 임계값 조절, `ExchangeLearningManager`, `AIAutoOptimizer`, AlphaArena 틱 피드백 등)와 수동 복기가 함께 갈 수 있음. “사람만 로그 고침”으로만 서술하지 말 것. |
| **음성 STT/TTS** | 공개 저장소 기준 **전면 음성 UI·라이브러리 통합이 없을 수 있음**. “이미 제품에 붙음” 대신 **로드맵·단계 공개**로 쓸 것. |
| **대외 단정** | 검증 불가한 **유일·세계 1위·모두 가짜 AI** 등은 `USER_GUIDE`·백서에서도 자제. **구조·로그·책임 경계** 등 검증 가능한 축 중심(인앱 메뉴얼 톤). |
| **실행 연계** | NoahAI 클라이언트는 사용자 설정 하에 **거래소·증권 API로 주문을 보낼 수 있음**. “실행 안 함”만 강조하면 IR용 백서와 충돌하므로, **법적 브로커 아님·체결 주체는 거래소·사용자**와 짝지어 쓸 것. |
| **인앱 본문 형식** | `user_manual_widget.py` 안의 메뉴얼 문자열은 `CTkTextbox`에 **평문**으로 들어가며 마크다운이 렌더되지 않음. 별표 두 개로 감싼 굵게(`**…**`)나 강조용 단일 `*`는 화면에 그대로 보이므로 **메뉴얼 코드에는 넣지 말 것**. 구분은 절 제목(━), 이모지, 「」인용 등으로 처리. |

### NoahAI 포지셔닝·메뉴·생활금융 확장 문서 정합 규칙 (2026-04 보강)

NoahAI 관련 문서에서 다음 기준을 공통 적용합니다.

1. NoahAI는 단순 자동매매, 수익률 중심 투자 플랫폼, 자산운용 상품으로 설명하지 않습니다.
2. 최상위 정체성은 `AI 금융 동반자`와 `AI 자산 의사결정 인프라`를 함께 사용하되, 문맥에 따라 구분합니다.
   - 사용자/제품 문맥: AI 금융 동반자, 쉬운 금융생활, 대화형 금융 어시스턴트
   - 기술/IR/R&D 문맥: AI 자산 의사결정 인프라, 판단·설명·기록·검증·환류 구조
3. 블록체인, 주식/증권, ETF, 글로벌 자산 등은 최상위 정체성이 아니라 하위 도메인 또는 실증·확장 영역으로 설명합니다.
4. 거래 데이터, AlphaArena, 실거래 로그는 수익률 홍보가 아니라 `AI 금융 의사결정 데이터셋`과 `판단-결과 환류 검증 자료`로 설명합니다.
5. 승률, 손익률, 차익거래, 자동화 거래 비율 등은 투자 성과 홍보 지표로 전면 배치하지 않습니다. 필요한 경우 내부 검증·리스크 통제·판단 품질 평가 지표로만 사용합니다.
6. 생활금융 확장 항목(대출 비교, 보험 선택, 사기 위험 탐지, 고령층 금융 보조, 개인 맞춤형 금융관리)은 구현 완료 기능처럼 쓰지 말고, 현재 상태를 `로드맵`, `설계 중`, `확장 예정`, `R&D 고도화 대상`으로 구분합니다.
7. `글로벌자산` 같은 메뉴명은 사용자가 이해하기 어려우므로, 문서와 UI에서는 목적 기반 명칭을 우선 검토합니다. 예: `자산 현황`, `자산 통합`, `글로벌 금융`, `금융생활`, `리스크 보호`.
8. 문서 수정 시에는 `투자 성과 중심`이 아니라 `사용자가 금융을 몰라도 이해하고 선택할 수 있게 돕는 구조`를 중심 문장으로 유지합니다.

### 현재 상태 표기 강제 규칙
1. 코드에 버튼/화면이 있고 사용자가 직접 눌러 결과를 볼 수 있으면 `기본 제공` 또는 `MVP 제공`으로 적습니다.
2. 계산은 되지만 저장/자동화/심화 추천이 없으면 `부분 구현`으로 적습니다.
3. 준비용 설정 키만 있고 대시보드 실행 경로가 닫혀 있으면 `실행 미완료`로 적습니다.

5. 과거 계획 문서가 남아 있더라도 현재 빌드와 충돌하면 상단에 `레거시/이력` 표기를 넣고 최신 정본 링크를 적습니다.

## 📊 판단 품질 지표 체계 (KPI Framework) — 2026-04 확정

NoahAI의 성과를 수익률·승률로 설명하는 대신, **AI 판단 인프라 품질**로 측정합니다.

### 핵심 판단 품질 지표

| 지표 | 정의 | 측정 기준 |
|------|------|-----------|
| **판단 로그 완결률** | 판단이 발생했을 때 근거·시각·결과가 모두 기록된 비율 | `recorder.py` 완결 로그 건수 / 전체 신호 건수 |
| **AI 판단 재현 가능률** | 동일 입력 조건에서 동일 판단이 재현되는 비율 | Replay 엔진 검증 결과 |
| **리스크 경고 적중률** | 경고가 발생한 후 실제 손실/위험 이벤트가 뒤따른 비율 | 위험 이벤트 / 전체 경고 건수 |
| **사용자 질문 해결률** | AI 어시스턴트가 사용자 질문에 완결된 답변을 제공한 비율 | 해결됨 표시 건수 / 전체 질문 건수 |
| **설명 만족도** | AI 판단 설명에 대한 사용자 수용 평가 | 설명 후 사용자 행동 추적 (확인/무시) |
| **의사결정 전후 사용자 행동 변화** | AI 판단 제공 전후 사용자의 거래/선택 행동 변화율 | 판단 전 기준 행동 vs 판단 후 행동 |
| **위험 선택 회피율** | AI 경고 후 사용자가 고위험 선택을 취소한 비율 | 경고 후 취소 건수 / 경고 발생 건수 |
| **금융상품 비교 정확도** | 대출·보험·예금 비교 시 정보 정확도 (R&D 지표) | 실제 조건과 제공 정보 일치율 |
| **사기 위험 탐지 재현율/정밀도** | 금융사기 탐지 엔진의 Recall/Precision (R&D 지표) | 탐지 건수 / 실제 사기 건수 |
| **AlphaArena 의사결정 시퀀스 수** | AlphaArena에서 LLM 판단 → 실행 → 검증까지 완결된 시퀀스 | 완결 시퀀스 건수 |
| **모델별 판단 일관성/차이 분석** | 다중 LLM 모델 간 동일 조건 판단 일치율 | GPT vs Claude vs Gemini 판단 비교 |

### 사용 규칙

- 문서에서 **승률, 손익률, 수익률, 차익거래 비율** 등을 단독 KPI로 전면 배치하지 않습니다.
- 위 지표는 내부 품질 검증·R&D 보고서·IR 자료에서 사용합니다.
- 사용자에게 노출되는 지표는 **판단 신뢰도, 리스크 경고, 설명 완결성** 중심으로 작성합니다.
- 생활금융 KPI(금융상품 비교 정확도, 사기 위험 탐지)는 **R&D 단계** 지표임을 명시합니다.
