# 3.9.2.0 고객 공유 자료 대조 및 전략 다중 선택

2026-10-01. 공개 설치본은 3.9.1.50, 수정 소스는 3.9.2.0이다. Windows 빌드·게시자는 사용자다.

## 자료와 경계

- 실제 자료 위치는 `data/261001_Teayu`다. 요청의 `261010_Teayu`와 날짜 철자가 다르다.
- 로그/호스트 이벤트/웹 명령 감사 및 `event_audit.sqlite3`를 읽기 전용으로 점검했다. 고객 앱을 실행하지 않았고 원본 DB·전략·설정을 수정하거나 주문하지 않았다. SQL은 `mode=ro&immutable=1`로 열었다.
- 기관별 텍스트 로그의 보존 범위가 다르다. OKX 텍스트는 10월 1일 구간만 남아 있고, 49/50 사건은 웹 명령 감사·이벤트 원장을 함께 대조했다. 신한/미래에셋 로그가 비어 있다는 것은 정상 운용의 증거가 아니다.
- 아래에는 고객 전략 내용·계좌·키·잔고·개별 주문을 전재하지 않는다. 회귀시험은 합성 자료다.

## OKX: 같은 실패 단계지만 세부 원인은 미확정

웹 감사 `runtime.command_rejected`, 2026-09-30 05:22:03.705977 UTC의 명령 ID가 신고의 `508f1d9354e9455dab19b3aba18a3572`와 일치한다. 원인은 `trading_candidates_unavailable`, 단계는 `candidate_selection`이다. 9월 29일 이후 같은 유형 거부가 16건이다. 거래 원장 복구 오류라는 근거는 없다.

고객 선정 설정은 최소 거래대금 15,000,000, 최대 변동률 25다. 이미 재현·수정한 **일괄 ticker 실패 → 개별 fallback에서 volCcy24h/open24h 누락 → 거래대금 필터 전량 제외**와 양립한다. 그러나 당시 원시 ticker/일괄 조회 실패 기록이 남아 있지 않으므로 이 고객 사건의 유일 원인으로 확정하지 않는다. 10월 1일 OKX 로그에는 후보 20개 확보·분석 기록이 있어 지속적 미지원도 아니다.

3.9.2.0은 원본 공개 ticker 근거 보존, 결측/0가격 거부, 목록/거래 가능 상품/시세/필터 제외 원인 분리를 유지한다. 이번에 후보 실패를 고객이 공유하는 기관 로그와 감사 경로에도 기록하도록 연결했다. 종목·계좌 payload 대신 원인 코드와 시장/후보/유효시세/통과 개수만 남긴다. 일반 logger에만 남아 실제 공유 자료에서 이유가 사라지는 관측 공백을 줄인다.

추가 코드 재현: 일괄 조회가 심볼 인자를 거부하여 인자 없이 재시도할 때, 두 번째 호출 예외가 개별 fallback 밖으로 빠져 후보가 0개가 되는 경로를 확인했다. 수정 전 1개 회귀 실패, 수정 후 통과했다. 두 번째 호출도 동일한 예외 처리 안에 넣어 기존 제한 병렬 fallback으로 이어지게 했다. 공통 경로 수정이므로 OKX만 특별히 필터를 우회하지 않는다. 이 재현 역시 당시 고객 통신 payload 부재 때문에 고객 사건의 확정 원인과 구분한다.

**다음 확인:** 새 Windows 빌드에서 같은 설정으로 OKX PAPER 시작, 일괄 시세 실패 및 복귀를 검사한다. 재발 시 새 코드와 같은 시각의 후보 개수 기록으로 구분한다. API 키 재발급·PnL 초기화·필터 해제를 일괄 권하지 않는다. 실제 고객 환경 해소는 아직 미확인이다.

## 키움: 기존 종료 수정과 연결되며 별도 조회 장애도 존재

- 9월 30일 10:12:03 UTC, 10월 1일 03:57:40 UTC에 `worker_shutdown_timeout`, `runtime_still_alive`가 함께 기록됐다. 이후 재종료에는 오류가 없는 기록도 있다.
- 첫 실패 전후 `get_stock_info` → opt10001이 10초 기다린 뒤 시간초과했고, 종료 실패 뒤에도 다음 조회가 이어졌다. 기존 수정의 **controller 취소 전파 → 읽기 대기 취소 → 정지 후 새 RPC 금지** 대상과 연결된다. 이미 전송한 주문/취소는 이 취소 경로에서 제외한다.
- 9월 30일 이후 호스트 자료에 opt10001 시간초과 3,874건, opw00018 497건, opt10075 386건이 있다. 이 수는 고객의 손실·주문 실패 수가 아니라 TR 조회 응답 시간초과 기록 수다. 같은 TR을 종목마다 반복 대기하는 일을 줄이기 위해 동일 TR 3회 연속 시간초과 후 30초 재시도 간격을 추가했다. 다른 TR과 주문은 차단하지 않으며 정상 응답 후 연속 실패 상태를 지운다.
- 별도: 9월 30일 21:31:19 UTC `get_live_readiness:TimeoutError` 뒤 기존 호스트가 23:02:31에야 요청 처리 기록을 남겼다. 조회 내부 TR 지연과 별도로 OCX/메시지 루프 또는 Windows 환경이 정지한 가능성이 있으나, 로그만으로 모달 창·절전·프로세스 스케줄링·OCX 원인 중 하나를 확정할 수 없다. 자동 재로그인 차단은 유지한다.

**다음 확인:** Windows 실제 x86 호스트로 조회 중 정지·종료, 절전/복귀와 장시간 운용을 확인한다. 이 환경 인수를 모의시험으로 완료 표시하지 않는다. 키움 자체 장애로 단정하지 않는다.

## 다른 기관 점검

- Binance: 49/50 감사에서 합의도·진입 위험조건 HOLD가 반복된다. 이것을 예외로 보고 보호 기준을 완화하지 않았다.
- Upbit: 요청 제한과 1초 백오프 안내 1건. Bybit: 후보 일시 미확보 안내 1건. KIS: 후보 목록 미확보 안내 및 50의 TLS `SSLError/SSLEOFError` 1건. 일시 외부 실패 자체를 소프트웨어로 없앨 수 있다고 하지 않는다.
- KIS 통신 예외 문자열에 계좌 조회 URL이 남을 수 있는 문제를 수정했다. GET/POST/토큰 오류는 요청 payload 없이 오류 종류를 기록한다. TLS 검증을 끄거나 주문을 자동 재전송하지 않는다.
- Bithumb/Coinone/Bitget의 보존된 최근 로그에서 추가 ERROR/CRITICAL은 찾지 못했다. 모든 계정·운영 시간의 무오류 보장은 아니다.

## 전략 다중 선택 정책과 사용

피드백은 합리적이다. 개별 작업은 있었지만 목록의 다중 선택 처리는 없었다. 기존 실행/승인 정책을 재사용하며 금융 실행 권한은 늘리지 않는다.

`전략 스튜디오 → 3. 내 프라이빗 전략 버전`에서 행의 **선택** 체크박스 또는 **현재 목록 선택**을 사용한다. 검색/필터/기관 변경 시 해제된다. 최대 100개 버전을 순차 처리한다. 이 작업 수와 일반 10/프리미엄 30 동시 평가 한도는 서로 다르다.

| 작업 | 처리 계약 |
|---|---|
| 선택 버전 삭제 | 선택한 버전만 삭제. 활성/검증 중 항목 보류. 다른 버전·거래 원장은 보존. 삭제 확인 필수. |
| 선택 일시중지 | PAPER는 근거를 보존해 중지, 최종 적용 버전은 신규 진입 풀에서 해제. 강제청산/기관 전체 정지가 아님. |
| 선택 PAPER 검증 | 기존 승인·실행식·한도·형제 버전 충돌 검사를 그대로 적용. 일시중지 근거는 이어서 사용. 자동 승인/초기화/LIVE 활성화 없음. |
| 선택 전략 내보내기 | 검증 passport 없이 정의만 담은 유효한 .noahstrategy 파일. |
| 선택 패키지 내보내기 | 기존 정의+검증 요약 패키지. 개별 체결 기록·승인·활성 권한 포함/자동 허브 게시 없음. |

내보내기는 한 번의 ZIP 다운로드로 제공한다(20MB 제한). 압축 해제 후 개별 `.noahstrategy`를 기존 가져오기로 열 수 있다. 패키지 기능 설정·IR 유효성·서버 권한 제한도 그대로 적용되며, 보완 필요 버전이 내보내기에 실패하면 개별 이유를 표시한다.

각 항목의 완료/보류/실패와 남은 작업 중단을 제공한다. 중단은 이미 처리된 작업을 되돌리지 않는다. 통신 실패는 저장 여부 미확정일 수 있으므로 자동 재시도하지 않고 새로고침 후 상태를 확인한다. 화면을 벗어나면 다음 요청을 중단한다.

## 검증 정본

시험 수와 최종 renderer 지문은 `TEST_STATUS.md`, Windows 인수는 `DEPLOY_CHECKLIST.md`를 따른다. 고객 원본이 없는 구형 fixture 시험을 이번 고객 자료로 임의 대체하지 않는다. 공개 설치기·원격 서비스 설정 변경 없이 소스/renderer 검증까지만 수행했다.
