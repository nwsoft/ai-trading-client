## 거래 차단의 원인과 패치 이력

스크린샷은 Binance의 기본/confirm 신규 진입 수익성 정책 차단을 보여준다. 거래소 API 장애라는 증거가 아니며, `미대조 0/300`은 300개 입력 행 중 미대조 0건이다. 화면의 adaptive 승률(14일/30건)은 Gate의 평가 범위(45일/최대 300건)와 다르다. 고객의 실제 정책·Hard MDD·설치 버전은 첨부만으로 확정할 수 없다.

현재 소스에서 재현하고 수정한 항목:

| 항목 | 수정 | 보존/변경 영향 |
|---|---|---|
| 거래소 부분 override가 전체 하위 정책을 대체 | Binance/Unified 모두 재귀 병합·깊은 복사 | 명시한 strict_stop과 개별 설정 유지. 설정 원본 변경 없음 |
| Binance 최신→과거 순서를 최근 성과로 해석 | 시각을 정규화해 과거→최신 정렬하고 최신 N건 선택 | 최근 구간·MDD가 실제 시간순으로 다시 산출되므로 수치가 달라질 수 있음 |
| 소표본에서 Hard MDD를 검사하기 전 통과 | Hard MDD 보호 검사를 소표본 분기 앞에 배치 | 소표본이라도 큰 손실이면 차단. 기존 계좌 한도/TP·SL/최종 주문 권한 코드는 그대로 |

| 통합 거래소 DB 읽기 실패와 빈 원장 혼동 | Recorder strict 읽기와 오류 표본 전달 | 조회 실패를 cold start로 처리하지 않음. 기존 일반 조회 호출은 기본 동작 유지 |
| 이유 없는 같은 문구 반복 | 상태·실제값·기준·적용 정책·출처·다음 조치 진단 및 로컬 재평가 API/UI | 재진단은 거래 시작/주문/정책 변경을 하지 않음 |
| 매번 이동하는 “N건 후 점검” | 각 주기·청산 후 재평가와 최근 평가 창 길이를 명시 | 존재하지 않는 진행률을 표시하지 않음 |

관련 변경 기록은 `docs/CHANGELOG.md`의 **2026-04-30 검증 계층 최초 추가**, **3.9.0.1(2026-07-24) 제한 회복 운용**, **3.9.1.22(2026-09-06) 순수익률·점진 위험 복구**, **3.9.1.43 손익 미대조 보호**다. 이 기록은 설계 변경의 증거다. 작업 폴더에 `.git`이 없고 공개 `nwsoft/ai-trading-client` 저장소에는 해당 Python 소스 이력이 없으므로 **각 결함의 최초 유입 커밋/배포 버전은 미확정**이다. 고객의 장애가 특정 수정 하나 때문에 발생했다고 단정하지 않는다.

## 사용자가 취할 수 있는 조치

새 소스 화면: **유지관리 → 거래 기록 점검·복구 → 수익성 진단 → 현재 근거로 다시 진단**. 엄격 중지의 일반 성과 미달, Hard MDD 보호, 손익 미대조, 수익률 근거 부족을 구분한다. 정책 변경은 기존 고급 매매 계층의 명시적 설정 저장을 사용한다. 실거래를 자동 재개하지 않는다. 증권 진단은 마지막 실행 주기의 실효 정책으로 PAPER 원장 또는 LIVE 확정 원장을 다시 읽는다. 모의 API 모드는 마지막 평가 결과만 사용하며 진단 때문에 증권사 API를 호출하지 않는다. 실행 근거가 없으면 미확인으로 표시한다. 진단 요약 파일은 검사값·기준·사유·출처만 내려받고 API 키·계좌 식별자·개별 거래는 포함하지 않는다.

구버전의 *부분 override 상속 손실*에 한정된 오프라인 복구:

```bash
python scripts/repair_profitability_policy.py --settings /path/to/settings.json --exchange binance
# 앱 전체 종료 후 미리보기의 변경 필드를 검토한 경우에만:
python scripts/repair_profitability_policy.py --settings /path/to/settings.json --exchange binance --apply --offline-confirmed
```

기본은 읽기 전용. 적용 시 권한 0600 원본 백업과 교체 파일을 만들고 원본이 도중에 바뀌면 중단한다. 출력에 API 키/정책 값은 넣지 않는다. 명시한 strict_stop을 limited_learning으로 바꾸지 않고, 원장/손실 한도/주문 권한을 초기화하지 않는다. 되돌릴 때도 앱을 종료하고 생성된 `.before-profitability-*.bak` 원본을 사용한다. 정상적인 성과 미달·Hard MDD·미대조·새 코드 오류까지 해결하는 범용 초기화가 아니다. 고객 설정이 이 경우에 해당하는지는 아직 확인되지 않았다.

## 생활금융에서 구현한 범위

- 검증 출처·권리 확인 참조·상품/기관/버전·확인 시각·만료·판매중지 상태를 보관하는 SQLite 카탈로그. 공급원별 완전 스냅샷을 트랜잭션으로 교체하며 실패하면 이전 데이터를 보존한다. 만료/판매중지 자료는 후보에서 제외한다.
- 대출: 세 가지 상환 방식, 거치, 실제 일수/365·360, 윤년/월말, 월별 원 단위 반올림, 추가 원금 상환·확인 수수료, +2%p 금리 가정, 월 부담·소득 감소·담보의 단순 비율. 금리 변경 일정과 기존·신규의 다른 상환 방식을 지원한다. 기존 계약 확인을 선택하면 각각의 비용·거치·일수·반올림·변동 금리를 같은 남은 원금/기간에 적용한다. 조건 미확인이면 절감액을 보류한다. 미확인 비용은 0으로 만들지 않는다. 단순 비율과 규정 참고를 구분한다. 날짜/차주 맥락이 일치하는 검토 규칙과 기관 확인 연간 원리금 산정액이 있을 때만 DSR/LTV 참고 비율을 별도로 계산한다. 실제 규칙 묶음·개인 승인 결과는 미확보다.
- 예금/적금: 목돈/월 납입, 단리/월복리/연복리·잔여월 단리, 월초/월말 납입, 입력 세율, 목표금액 역산, 확인한 중도해지 금리, 목돈 만기 세 구간 분산. 자유 납입/누락 월과 부분인출의 중간 수령·만기 잔액, 확인한 우대금리/상한·과세 규칙·동일 기관 예금보호 합산을 추가했다. 기간별 실제 은행 금리는 자동 생성하지 않는다. 세율/중도해지 금리가 없으면 해당 세후 금액은 미확인.
- 보험: 없음/기존/모름과 12개 보장 종류별 확인 질문, 요구 보장 대조표, 개인 견적 확인·월 예산을 전제로 최소 부담/요구 보장과 예산 균형/미확인 보장 우선 검토의 세 설계안. 유지·추가·교체의 월 부담/확인한 해지 손실 비교. 약관 지급·재심사·중복 지급을 자동 확정하거나 보장 점수로 우승 상품을 만들지 않는다.
- 세 영역 공동 월 예산의 잔여액과 새 대출 상환 반영. 미입력 금액은 미확인으로 유지.
- 결과·조건·규칙 버전을 기존 계정별 암호화 vault에 저장/조회/삭제하고 기존 암호화 백업에 포함. 저장 시 서버에서 재계산. 잠금/시간 만료 시 개인 화면 정리. 상담 준비 Markdown 내려받기는 사용자가 실행한다. 지정 상담사 파일 전달/접수번호 직접 기록, 기관 API 전송·상태·철회 연결부를 추가했다. 실제 수신처 미등록 상태에서는 발송하지 않는다. 만료·상품 버전 변경·예약 재점검일도 보관함에 표시한다.
- 후속 질문: 현재 비교 입력에서 명확한 금액/기간/예산/복리/거절한 우대 조건을 반영하고 다시 계산한다. 변경 전후 차이와 각 견적의 비용·보장·출처·유효기한을 설명한다. 여러 금액/기간은 확인 질문으로 남기고 음수를 양수로 해석하지 않는다. 일반 어시스턴트는 기존 로컬 문맥 설명을 유지한다. 항목명이 있는 복수 금액·기간을 함께 변경하고 12개 보험 유형·부양가족·직업·확인된 기존 보장을 다룬다. 유효 근거 문단 검색과 출처/쪽/버전을 추가했다. 일반 어시스턴트도 최근 사용자 조건을 재구성해 현재 상품 근거로 답한다. 선택 AI 설명은 전송 내용/모델/hash 미리보기와 별도 동의를 거치며 일반 캐시 저장을 끈다. 모든 자유 문장·전문 금융 판단의 정확도를 인증한 것은 아니다.
- 직접 받은 견적 최대 20개, 명시한 유효기한이 지난 견적 제외, 탭 전환 시 메모리 입력 유지, 보관함 잠금 시 관련 비교 화면 즉시 정리. 저장 결과는 과거 스냅샷으로 표시하고 현재 기준 재계산을 구분한다.
- 구형 대출/예적금 API와 어시스턴트/위젯에서 검증되지 않은 예시 카탈로그 추천, 필터 완화, 신용점수에 따른 임의 금리 조정을 제거했다. 기존 카탈로그 파일은 삭제하지 않는다.

등록한 로컬 JSON 공급 파일은 화면 접근 시 15분 주기로 갱신 여부를 확인하며, 수동 재확인은 최소 5초 간격이다. 실패 시 마지막 정상 자료를 유지하고 최대 1시간으로 제한된 재시도 간격을 적용한다. 검토된 이전 revision으로 복원하면 해당 공급원 자동 갱신은 중지한다. 파일 경로와 원시 오류는 화면/API에 공개하지 않는다. 서버 상시 스케줄러·공식 금융기관 API 연결 완료를 뜻하지 않는다.

카탈로그 운영 도구: `scripts/import_finance_product_catalog.py --database <account-data>/finance_product_catalog.sqlite3 --snapshot <reviewed-source.json>`. JSON은 `source: {id,url,rights_verified,rights_reference}`, `products: [{id,name,provider,kind,version,source_url,verified_at,valid_until,status,terms}]`를 요구한다. `verified_at/valid_until`은 시간대 있는 ISO 시각이다. 이 도구는 검토자가 제공한 자료를 가져오며 **공식 기관의 검증·API 권한·주기 수집 계약을 대신하지 않는다.** 확인되지 않은 실상품을 넣어 건수를 채우지 않았다. `--register-feed`는 해당 스냅샷 파일의 갱신을 등록하고, `--refresh`는 등록 공급원을 확인하며, `--rollback-revision <revision>`은 검토된 이전 자료를 복원한다.

일반 설명 참고 자료는 [보험연구원의 운전자보험 소비자 유의사항](https://www.kiri.or.kr/report/downloadFile.do?docId=6005), [저축은행중앙회 비교공시 이용 안내](https://www.fsb.or.kr/ratuserguide_0100.act)다. 해당 문서는 현재 특정 상품의 가입 조건/개인 견적 데이터로 사용하지 않는다.

추가 운영 보완:
- 로컬 파일/API 갱신과 복원은 동일 잠금을 사용한다. API 설정 오류는 상품 수동 비교까지 중단시키지 않는다.

- 지정 상담사 전달 파일 생성은 접수가 아니다. 사용자 입력 접수번호/처리 결과는 기관 검증과 구분한다. 로컬 삭제와 기관 삭제 완료도 구분한다.
