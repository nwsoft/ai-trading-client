# v3.9.0.8 Fix 2 실행 증거와 Fix 4 Windows 메뉴 자원 근본 수정

기준일: 2026-08-11  
상태: Fix 4 소스 수정·자동 회귀 진행, 공개 Windows EXE는 Fix 2

## 결론

2026-08-11 23:34 제보 화면의 창 제목은 `v3.9.0.8 AI Custom Update Fix 2`다. 현재 공개 `deploy/release-manifest.json`도 Fix 2 EXE와 SHA-256 `c1edaf84410f...`를 가리킨다. 따라서 이 화면은 Fix 3/4에서도 같은 장애가 재현됐다는 증거가 아니라, Fix 3/4 Windows 자산이 아직 설치·배포되지 않았다는 증거다.

동시에 Fix 2가 해결을 표방한 화면에서 `No more menus can be allocated`와 금융 인텔리전스 순서 이탈이 계속된 것은 Fix 2 방어가 충분하지 않았다는 뜻이다. 실행 자체와 일부 CustomTkinter 화면·로그가 정상인 점은 필수 DLL 전체 누락보다 native 메뉴 자원 고갈과 부분 할당 실패에 부합한다.

따라서 `화면 한 곳 수정 → 같은 이름의 EXE 재배포` 방식은 중단한다. Fix 4는 실행 파일 신원, 업데이트 상태 전이, native 메뉴 할당 상한, UI 소유권·재사용, 탭 정본, 빌드 런타임을 각각 독립 계약으로 검증한다.

## 확인된 근본 원인

1. 종료 순서 역전
   - 기존 흐름은 거래소·DB 안전 종료 뒤 업데이트 preflight를 다시 실행했다.
   - 이미 중지된 어댑터는 `exchange_state_read_failed`가 되어 정상 적용도 차단할 수 있었다.
   - Fix 2는 `종료 전 승인 → 안전 종료 → 승인 소비` 순서만 허용한다.

2. 정상 새 EXE의 오판 롤백
   - 재시작 약 1초 뒤 활성 거래소 API가 모두 준비돼야 health check를 통과했다.
   - 네트워크·거래소 초기 연결 지연만 있어도 새 EXE를 실패로 보고 이전 EXE 복원을 예약할 수 있었다.
   - Fix 2는 유지 포지션이 없으면 API 초기화 지연을 advisory로 처리한다. 유지 포지션이 있으면 최대 30초 재시도 후 포지션을 엄격 비교한다.

3. 같은 버전 패치의 신원 부족
   - `3.9.0.8` 문자열만 같으면 새 Fix가 실제 설치됐는지 판단할 수 없다.
   - Fix 2는 다운로드 파일, 복사된 설치 EXE, 재시작 후 설치 EXE의 SHA-256을 manifest와 비교한다.

4. 업데이트 저널 경쟁과 재시도 손실
   - 부모 PowerShell이 새 앱 실행 후 늦게 `postcheck_pending`을 기록해 새 앱의 `healthy`를 과거 단계로 덮을 수 있었다.
   - `apply_scheduled`, `replacing`, `failed` 단계에서 재시작하면 staged 파일을 pending으로 복원하지 않아 한 번 실패한 업데이트가 사라졌다.
   - Fix 2는 시작 전에 `postcheck_pending`을 기록하고, 실패 단계의 검증된 staged EXE를 재시도 대상으로 복원한다.

5. 불필요한 화면 전체 재생성
   - 같은 서비스 버튼 재클릭, 동일 설정 저장, 공통 AI 탭 보장 과정에서도 살아 있는 탭을 파괴·재생성했다.
   - 탭 스타일 적용도 현재 선택 대신 첫 탭을 선택해 사용자가 탭 순서·선택이 바뀐 것으로 체감했다.
   - Fix 2는 동일 서비스·동일 source 구성과 살아 있는 공통 AI 위젯을 재사용하며 현재 선택을 보존한다.

6. 부분 렌더를 정상으로 취급
   - 네이티브 자원 할당 중 한 섹션 생성이 실패해도 내부 예외가 숨겨져 포지션 또는 로그 일부만 남을 수 있었다.
   - Fix 2는 제어·잔고·포지션·통계·로그 완전성을 검사하고 일부만 생성되면 `service_tab_partial_render`로 fail-closed 처리한다.

7. native 메뉴를 사후 정리에 의존
   - CustomTkinter 5.2.2는 CTkComboBox·CTkOptionMenu 생성 때마다 Windows `tk.Menu`를 하나씩 영구 생성한다.
   - Fix 1/2는 탭 파괴 때 메뉴를 회수하고 설정창을 재사용했지만, 정리 경로가 한 번이라도 누락되면 누적을 막지 못했다.
   - Fix 4는 Windows에서 드롭다운을 클릭한 동안에만 프로세스 전체 최대 1개 native 메뉴를 만든다. 닫기·선택·다른 드롭다운 열기 때 즉시 폐기해 사후 정리 누락과 무관하게 상한을 둔다.

8. 설정 범위와 실행 상태의 UI 혼합
   - `거래소: BINANCE`는 다중 거래소 사용자를 단일 거래소처럼 보이게 했고 `상태: 전체정지`는 API/설정이 꺼졌는지 워커가 멈췄는지 구분하지 못했다.
   - Fix 4는 `거래소: 6곳 · 기준 BINANCE`와 `자동매매: 정지 (0/6 실행)`으로 분석 범위·현재 기준·실행 상태를 분리한다.

9. 탭 지연 생성 뒤 순서 재적용 누락
   - 기능 탭과 거래소 탭 생성 시점이 달라지면 금융 인텔리전스가 마지막에 추가될 수 있었다.
   - Fix 4는 새 탭이 생길 때마다 프레임을 파괴하지 않고 정본 순서만 idle에서 재적용한다.

## DLL·버전 판정

- PyInstaller spec은 `tkinter`, `tkinter.ttk`, `tkinter.messagebox`, `customtkinter`를 명시 포함한다.
- Windows 빌드는 Tcl/Tk 사전검사 실패를 차단하고, PyQt5·pandas 등에 중복된 VC 런타임을 제거한 뒤 공식 VC143 단일 세트를 넣어 버전·SHA를 검사한다.
- Tk 또는 필수 DLL이 빠졌다면 일반적으로 앱 시작·import·위젯 생성 자체가 광범위하게 실패한다. 현재처럼 앱과 로그가 실행되면서 반복 전환 뒤 일부 섹션이 비는 증상만으로 DLL 누락을 원인으로 확정할 수 없다.
- 최종 판정은 Fix 4 Windows 빌드 로그, EXE 아카이브 검사, 제보 PC 실행 SHA와 USER/GDI/TK_MENU 반복 측정으로 한다.

## Fix 4 배포 계약

1. 현재 공개 Fix 2와 다른 Fix 4 EXE SHA-256을 만든다.
2. 빌드 로그에서 Tcl/Tk·VC143·PyInstaller 아카이브 검사를 통과한다.
3. Fix 4 EXE와 `release-manifest.json`을 같은 GitHub release에 함께 게시한다. EXE만 바꾸거나 manifest만 바꾸지 않는다.
4. 제보 PC에서 Fix 4 창 제목과 설정 → 업데이트의 현재 SHA 앞 12자리·배포 SHA 앞 12자리가 같은지 확인한다.
5. 다음 same-version 시험 자산으로 자동 다운로드·종료 전 승인·교체·재시작·health·사용자 재개까지 검증한다.
6. 설정 100회와 블록체인↔주식 100회 동안 빈 설정창, 거래소/증권사 혼합, 탭 선택 이동, 부분 섹션, `No more menus`가 0건이고 USER/GDI가 상한 안에서 안정돼야 테스터 배포 완료로 판정한다.
7. 유휴 로그의 `TK_MENU`는 0, 드롭다운을 연 순간에도 최대 1이어야 한다. 계속 증가하면 실패다.
8. 금융 인텔리전스가 모든 거래소 탭보다 앞에 있고, 다중 거래소/자동매매 상태 문구가 실제 설정·워커 수와 맞아야 한다.
