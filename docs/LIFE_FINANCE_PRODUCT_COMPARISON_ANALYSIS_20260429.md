B는 ‘테스터 실거래만 남음’이 아니라 데이터/계약/법무/개발이 필요한 조건부 범위다. 3.9.2.2에 포함하려면 해당 조건과 개발·시험을 모두 완료해야 한다. 그렇지 않으면 UI/홍보/상담 버튼에서 지원 완료로 표시하지 않고, A 완료판으로 범위를 명확히 확정한다. A는 B의 성과나 전 보험사 비교를 약속하지 않는다.

### 4. 사용자 화면과 상태 전이

생활금융 기존 금융상품 영역 안에 `내 보험 이해·비교` 진입을 두고 기존 대출/예적금 경로를 보존한다. 신규 독립 서비스나 전역 글꼴 변경으로 확장하지 않는다.

1. **첫 화면:** 확인된 계약 수, 이번 달 확인된 보험료, 갱신/만기 일정, 먼저 확인할 항목. 금액/날짜 미확인은 0원이나 정상으로 바꾸지 않는다.
2. **자료 등록:** 지원 형식·한도·보관/전송 정책 안내. 암호 문서·OCR 실패·누락 페이지·지원하지 않는 형식은 이유와 수동 입력 대안을 제공.
3. **추출 확인:** 원문과 항목을 나란히 표시. 상품/피보험자 구분·보장명·금액·기간 등 중요 필드와 매핑 불확실성은 사용자가 확인하기 전 확정하지 않음.
4. **보장표:** 보장 조건/제외·갱신·자기부담·근거·확인 여부. 요약에는 쉬운 문장을 쓰되 자세한 약관을 펼쳐 확인 가능.
5. **비교:** 기존 유지 / 계약 내 조정 가능성 / 추가 계약 / 교체의 자료상 차이. 실행 가능한 선택인지 보험사 확인 여부를 별도 표시.
6. **상담 준비:** 해결되지 않은 질문·선택 자료·민감정보 마스킹을 미리 확인한 뒤 로컬 저장. B2 활성화 전에는 외부 상담 접수 기능 없음.

예정 상태: `draft → extracting → needs_confirmation → reviewed → analysis_ready`. 실패·취소는 별도 상태와 재개/정정 방법을 남긴다. `reviewed`는 계약 유효성·보험금 지급·전문가 검증 보장이 아니다. 자료 변경 시 기존 분석은 이전 버전으로 보존하고 현재 결과를 `needs_reanalysis`로 표시한다. 원문 삭제 시 근거를 계속 조회할 수 있는 것처럼 표시하지 않는다.

### 6. 분석 규칙과 쉬운 설명

- LLM은 확인된 항목과 검색된 원문을 설명한다. 보험료 합산·기간·차액은 결정적 코드로 계산하고, 보장 지급 확정/의학적 진단/인수 심사는 하지 않는다.
- 중복 가능성을 실손 비례보상과 정액 지급 등 계약의 지급 방식에 따라 나눠 확인한다. ‘중복=불필요/해지’ 규칙 금지.
- 자료에 없는 보장은 ‘등록 자료에서 확인하지 못함’이다. ‘사용자는 미가입’ 또는 ‘반드시 가입해야 함’으로 바꾸지 않는다.
- 부족 가능성은 사용자 목표·부양/상환 부담·기존 계약 범위와 가정에 연결한다. 근거 없는 권장 가입금액/질병 확률/공포 점수 금지.
- 절감액은 동일 기간·보장 범위·납입 조건의 확인된 자료에 한해 가정으로 계산. 갱신형 보험료 불명, 건강 재심사, 인수 거절, 면책 재시작, 해지환급 손실, 보장 축소를 숨기지 않음.
- 기존 보험료가 가계부에 이미 등록되었는지 대조하기 전 자동 지출 추가 금지. 보험료 계획과 실제 납부 기록, 보험금과 자산 잔액을 구분.
- 근거가 상충하면 우선순위를 임의 결정하지 말고 해당 자료·상충 부분과 보험사 확인 질문을 표시. 번역/쉬운 설명에서도 중요한 제외 조건을 생략하지 않음.
- 답변 형태는 `확인된 사실 → 쉬운 설명 → 확인할 사항 → 근거 보기`로 통일. `유지 검토 가능`과 `추가 확인 필요`를 구분하며 판매 전환을 기본 결론으로 두지 않는다.

### 7. 보안·외부 AI·성능·호환성

- 계정별 자료 격리·접근 통제·암호화 저장/키 관리·백업/삭제 정책을 A2 개발 전 확정한다. 저장소가 로컬이라는 이유로 평문 민감정보 저장을 허용하지 않는다. 백업·내보내기에도 동일 경계를 적용한다.
- 건강정보/가족 자료는 별도 권한·민감정보 처리 범위를 확인한다. 가족 자동 수집/자동 공유는 범위 밖이다. 로그/오류진단/텔레메트리에 원문·건강정보·연락처·증권번호를 넣지 않는다.
- 외부 AI 사용은 전송 필드/수신 Provider/목적/비용을 보여준 별도 선택이며 미선택 기본 경로는 외부 미전송. 비식별화만으로 익명성을 보장하지 않는다. Provider 보관/국외 처리 조건도 검토한다. 외부 모델 없을 때도 수동 정리·결정적 비교·근거 확인 경로를 제공한다.
- 업로드 문서와 링크의 지시는 데이터로만 처리한다. 문서 내 프롬프트·스크립트·외부 URL을 따라 실행하거나 자동 전송하지 않는다. 파일 확장자뿐 아니라 실제 형식/압축 폭탄/해제 경로/손상 파일 검사.
- 초기 지원 목표는 PDF/PNG/JPEG와 수동 입력이다. 암호 파일 비밀번호는 영구 저장하지 않으며 이번 화면에서 지원하지 못하면 이유를 표시한다. 폴더/Drive/ZIP 일괄 수집은 별도 범위다.
- 초기 한도 설계값: 파일당 20MB·PDF 100쪽·작업당 5파일·계정당 동시 분석 1개. 기존 한도와 충돌 여부를 구현 전 확인하고 실측 후 확정한다. 한도 초과는 조용히 잘라 분석하지 않는다.
- 문서 처리/외부 호출은 거래 루프와 분리한 취소 가능한 작업으로 수행. 화면 조회/탭 진입이 OCR·AI·전체 카탈로그 갱신을 시작하지 않는다. 동일 hash+추출/규칙 버전 캐시와 제한된 재시도를 사용한다.
- 기존 계정별 가계부·이체·목표 파일, 전략·거래 원장과 분리한 버전 있는 저장소를 사용. 기존 카탈로그는 출처 미검증/예시로 유지하고 고객 계약으로 자동 마이그레이션하지 않음.
- 새 응답의 `best=null`/상태 enum은 Web·기존 UI·어시스턴트·내보내기 모두 함께 수정한다. 구 UI에 임의 `best`를 보내 호환성을 가장하지 않는다. 혼합 버전은 호환 오류와 업데이트 안내로 처리한다.

### 8. 상담 연결·수익화의 승인 조건

메리츠 파트너스는 설계사 자격 취득과 보험 계약을 통한 수수료 구조를 안내한다. 일반 링크 제휴나 NoahAI의 모집 자격·API 이용권 확보를 뜻하지 않는다. 전 보험 비교의 근거도 아니다. 공식 페이지의 수익 사례를 NoahAI 매출 전망으로 전용하지 않는다. [공식 안내](https://meritzpartners.com/)

보험 모집 수수료에는 제한이 있으며, ‘상담 연결비’나 ‘소프트웨어 이용료’라는 명칭만으로 적법성이 보장되지 않는다. 개인화 추천·가입 연결의 실제 흐름을 기준으로 등록/중개/광고/특례 적용 여부를 전문 법률 검토하고 필요 시 당국에 확인한다. 단순 보고서도 개인화 권유와 결합되는 방식에 따라 검토해야 하므로 A 역시 무규제라고 선언하지 않는다. [보험업법 제99조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1027001989), [금융위 플랫폼 적용 사례](https://www.fsc.go.kr/no010101/76485)

- B 활성화 전 확정: 제휴사의 등록/권한·상품 범위, NoahAI 역할·책임, 비교 기준, 수수료/환수/정산, 민원·불완전판매 대응, 데이터 사용권, 정보 전달·보관·철회/삭제 처리, 보안 사고 책임.
- 순서 제안: 소비자 보험 정리/관리 → 등록 보험사·GA용 근거 분석 도구 → 적법성이 확인된 상담·판매 제휴. 모든 유료 모델도 실제 업무 범위로 검토.
- 분석 로직에 수수료를 입력하지 않고 광고/제휴 노출은 별도 표시. 제휴 범위 밖의 상품을 비교했다고 하지 않는다. 가입 없이 유지·상담 종료도 정상 처리.
- 사업 판단 지표: 사용자 이해도·근거 정확성·민원·계약 유지·동의 철회, 그리고 고객 확보/문서 검증/상담/환수 비용을 포함한 순수익. 전환율만 최적화하지 않음.
- 2026-07 제도 개선과 2027-01 예정 분급제 등 시행 시점을 구분하여 실제 제휴 시 재검토한다. 수수료율·수익을 고정 가정하지 않는다. [금융위 2026-06-30 발표](https://www.fsc.go.kr/no010101/87217)

역할은 필요한 책임이지 담당자 배정 완료를 뜻하지 않는다. 보험 도메인 검토자·법무 검토 주체·자료 이용권이 미정이면 제품 담당자가 확정해야 한다. 달력상 출시일이나 ‘며칠이면 완벽’은 약속하지 않고 선행 조건과 완료 증거로 진행한다.

### 10. 필수 시험과 출시 기준

- [ ] **도메인:** 정액/실손, 면책/감액, 갱신/비갱신, 만기/납입 종료, 해지/실효, 과거/현재 약관, 정정/상충을 구분. 미확인을 미가입/보장 0으로 변환한 사례 0.

- [ ] **개인정보:** 계정 전환·삭제·백업/복원·내보내기·외부 AI 미동의에서 다른 계정 자료/원문/민감정보 유출 0. 문서 프롬프트 공격·악성 형식·권한 없는 URL 차단.

- [ ] **성능:** 3.9.2.1과 같은 Windows 환경/데이터/거래 부하로 분석 OFF/ON 비교. 초기 목표는 거래 사이클 p95 지연 증가 10% 이내, 일반 UI 조작 p95 200ms 이내, 분석 중 추가 메모리 300MB 이내·반복 종료 후 증가 추세 없음. 예비 설계값이며 구현 전 기준 장비/표본/측정법을 고정하고 초과 시 작업 분리·한도 개선 후 재시험. 미측정을 통과로 기록하지 않음.

- [ ] **Windows/롤백:** 실제 설치·3.9.2.1 업그레이드·재시작·자료 보존·롤백. 구버전은 신규 보험 자료를 수정하지 않고 신규 자료는 재업그레이드 후 보존. 소스·빌드·설치본 식별 일치.
- [ ] **B 전용:** 법무/권리/제휴 승인, 수신자 자격, 동의 확인, 전송 중복 방지, 실패/복귀, 접수 확인, 철회/삭제 요청 결과, 수수료와 추천 분리, 정산 대조. 미충족 시 비활성 유지.

시험 증거는 mock/정답셋/격리 화면/실제 설치/동의된 제휴 환경으로 구분한다. 실제 고객 보험 자료를 허락 없이 fixture로 복사하지 않는다. 새로운 약관/추출기/규칙/모델 버전도 고정 평가셋을 재실행한다. 구조화 출력 성공이나 JSON 유효성만으로 보험 정확성을 인증하지 않는다.

## 2. "왜 더미 데이터인가?" — 구체적 이유

### 2.1 기술적 이유

#### 문제 1: 금융사 데이터 접근 제한
| 데이터 소스 | 접근성 | 현실 |
|----------|--------|-----|
| 공개 웹사이트 | 낮음 | 금리/상품 정보는 공개이나 API 없음 |
| 금융감독원 API | 낮음 | 제한적·특정 금융사만 포함 |
| 각 금융사 API | 극히 낮음 | ☒ 엔터프라이즈 파트너십 필수 |
| 핀테크 데이터 서비스 | 중간 | 💰 월정액 비용 (수백만원+) |

**결과**: MVP 단계에서 실제 데이터 연동 불가능 → 더미 데이터로 구조만 검증

#### 문제 2: 데이터 정규화의 복잡성
- **금융사별 상품 분류 다름**: KB국민은행 "주택담보대출" ≠ 신한은행의 동등 상품
- **금리 표시 방식**: 고정금리 vs 변동금리, "초저금리 + 우대금리" 혼용
- **수수료 구조**: 월료, 사무비, 선결제 등 다양
- **보험 보장 범위**: "특약"이 복잡하고 금융사별로 다름
- **예적금 세금**: 이자 소득세(15.4%), 비과세 적금 여부 등

→ **한 금융사의 데이터 정규화에만 수주 소요**

#### 문제 3: 규제·법적 이슈
- **금융감독원 규제**: 부정확한 상품 정보 제공 시 금융상품판매조사 대상
- **신상정보 법령**: 사용자 신용도/소득 수집 시 규제 대상
- **광고법**: 특정 상품 "추천" 표현 시 이해상충 심사 대상

→ **실제 기능화 전 법무 검토 필수**

| 기능 | 구현 여부 | 동작 | 평가 |

- ✅ **프로토타입 수준의 "비교" 기능은 작동**

## 부록: 금융사 API 파트너십 난제 (참고용)

### A.1 왜 금융사는 데이터를 공유하지 않는가?

1. **신용 정보 보호법**: 고객의 금리/상품 정보는 민감정보
2. **경쟁 우려**: 자사 상품의 비교 공시는 고객 이탈 위험
3. **규제 시장**: 금융감독원의 승인 없이 3rd party 연동 불가
4. **기술 비용**: 각 금융사가 API 개발/유지 비용 부담 불원함

### A.2 해결 방법 (글로벌 성공 사례)

- **미국**: LendingTree, NerdWallet이 금융사 API 정보 수집 (자사 마케팅으로 상쇄)
- **영국**: FCA 오픈뱅킹 규제 (금융사 API 공개 의무화)
- **한국**: 정부 "오픈뱅킹" 표준 (2022~), 금융위 규제 샌드박스

**한국 내 현실적 경로**:
1. 금융위 규제 샌드박스 신청 (정부 공식 경로)
2. 오픈뱅킹 표준 API 활용 (이미 구축됨)
3. 금융사와의 개별 MOU (대형 금융사 + 핀테크 협력)
