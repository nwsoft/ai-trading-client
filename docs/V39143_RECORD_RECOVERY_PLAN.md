# 3.9.1.43 거래 기록 유지관리 구현 및 배포 조건

2026-09-20 · 제품 3.9.1.43 / updater 3.9.143 · 공개42 유지 · **배포 보류**.

[자동시험·실제 화면·DB 복사본 검증 보고](../reports/v39143-record-recovery-verification.md)

## 목표와 현재 판정

일반 사용자는 기존 시작/정지와 AI 자율운행을 유지한다. 기록 이상은 설정 → 업데이트 → 유지관리 → 거래 기록 점검·복구에서 처리한다. 별도 투자 모드나 수익성 우회 설정을 만들지 않는다.

**청산 주문 ID가 없는 Binance 기록도 거래소 과거 원장을 수집해 복구하는 경로를 구현했다.** 이전의 “로컬 보호 주문 근거 없음 → 즉시 종료” 경로를 대체한다. 확인된 진입 주문과 완전한 포지션 구간으로 소유권을 증명하며 가격·시간 유사 매칭으로 대체하지 않는다. 고객 API 응답을 받지 않은 상태에서 특정 고객의 40건이 복구됐다고 주장하지 않는다. 다른 기관의 미구현 historical adapter와 귀속이 섞인 계좌의 조건부 재개까지 완성됐다는 뜻도 아니다.

## 구현

- `trading/record_recovery.py`: 계정 DB별 한 작업, 별도 SQLite 작업 원장, 프로세스 간 120초 lease, 행별 체크포인트, 최초 SQLite online backup(WAL 포함), 이전 작업 변경 근거 보존. 백업 실패 시 API/복구를 진행하지 않는다.
- 최근45일 LIVE/owned 종료 기록을 점검하며 최근300건으로 잘리지 않는다. PAPER는 제외한다. 실행당90초/대략60 provider 요청 예산 후 이어서 실행. 단일 거래의 보호 주문 확인과 진입/청산 비용 복구에 최대6개 요청이 필요하여 예산 경계에 최대5개 초과할 수 있다. 거래 API의 자체 타임아웃은 별도 적용된다.
- 조회와 SQLite 쓰기 트랜잭션 분리. 상태 polling은 작업 집계만 읽으며 전체 trade_log나 외부 API를 다시 조회하지 않는다. 매 거래 사이클/앱 시작 시 전체 복구를 자동 실행하지 않는다.
- `record_recovery_adapters.py`: 정확한 청산 주문의 fill identity/방향/수량/날짜/유효 수수료 검사. 공유 진입 주문은 비용을 임의 배분하지 않는다. 유일한 진입 주문이 확인된 경우 누락된 진입 수수료를 실제 체결로 보강한다.
- Binance `get_recovery_order_fills`: 날짜를 생략한 최근7일 기본값 대신 기록된 주문일 주변2일의 명시적 조회. API 실패를 빈 목록으로 숨기지 않는다.1000건 포화 응답은 전체 확인으로 처리하지 않는다.
- 이미 저장된 진입→보호 주문→actualOrderId 증거가 있는 Binance TP/SL은 대상 행별로 재조회한다. 과거 시간/가격/수량 유사성만으로 수동 거래를 NoahAI 거래로 채택하지 않는다.
- `binance_history_recovery.py`: 보호 주문 근거도 없는 Binance 거래는 API의 userTrades/allOrders/allAlgoOrders/income를 종목·기간으로 수집한다. 6일 이하 구간, 1000건 포화 시 시간 범위 이분할, 빈 응답과 오류 분리, 완전한 범위 확인, 계정 키 지문별 영속 페이지/체크포인트를 적용한다. 같은 1ms에 1000건 이상이면 완전 조회로 속이지 않는다.
- 거래소 포지션 수량·변경 시각을 수집 전후 확인하고, 해당 시점까지의 전체 체결을 역산하여 과거 진입 직전 flat → 해당 주문 진입 → flat 청산을 입증한다. 여러 진입이 섞이거나 기존 보유분이 있으면 억지 배분하지 않는다. 롱/숏, hedge positionSide, 분할 진입 체결, 여러 주문의 부분청산을 지원한다.
- 체결 실현손익과 income의 tradeId별 REALIZED_PNL을 교차 대조하고 실제 진입·청산 수수료를 차감한다. 원래 거래 행과 기존 체결 원장에 반영한다. 여러 청산 주문은 claim 테이블에 실제 fill/order 목록을 보존하고 단일 exit_order_id에 가짜 값을 넣지 않는다. 펀딩을 개별 거래에 임의 배분하지 않으며 이는 계좌 전체 일별 PnL 인증과 별개다.
- 동일 작업 재시작은 저장된 수집 위치를 사용한다. 사용자가 새 점검을 요청하면 지연 체결/정산도 다시 조회한다. 최근 기록을 우선 처리하고 과거 원장 요청 사이 최소1.5초 간격(운영 기본값)을 두어 거래 엔진 API 호출 여유를 남긴다. UI가 열린 동안 요청 예산 이후 자동 이어하기, 닫힌 뒤 다음 실행 시 이어하기를 지원한다.
- recorder의 선택적 `reconcile=False` 저장 및 `trade_ids` 재대조로 유지관리 fill마다 전체 원장을 스캔하지 않는다. 기존 기본 호출 계약은 유지한다.
- 진입 수수료 NULL을 과거 총수수료 `fees` 또는0으로 대신하여 순손익을 확정하던 경로를 제거했다. 실제 기관 gross PnL은 보존하되 net PnL은 미확정으로 남기고 정확한 진입 주문으로 비용을 복구한다. 기존 비용 없는 테스트 fixture도 NULL 대신 명시적0 근거를 사용하도록 수정하고 NULL/총비용 혼동을 별도 회귀시험한다.
- 한국어/영어 유지관리 화면, 코인·주식 거래 통계 공통 진입점, 사유/처리/확인/남은 건수. 미대조 관련 경고에 실제 설정 경로를 연결하되 단순 성과 저하에는 복구를 권하지 않는다.
- 증권 LIVE 튜닝은 미확정 거래를 버리고 확인된 일부 승자만으로 승률을 계산하지 않는다.

## 안전 경계

점검은 외부 읽기 API만 사용하며 주문 제출/취소/강제 청산/새 거래 시작/위험 한도 초기화를 하지 않는다. API 키나 계좌번호를 작업 응답에 노출하지 않는다. gateway token과 confirmed intent가 필요하다. 최초 전체 런타임 생성은 AI 최적화도 시작하므로 유지관리에서 몰래 생성하지 않는다. 기존 계좌 연결이 필요하면 대시보드의 실시간 새로고침 안내를 제공한다. 키움 호스트를 유지관리 worker에서 재로그인하지 않는다.

**이미 실행 중인 엔진은 유지된다.** 복구된 근거로 기존 정책을 다시 평가하여 다음 사이클에 진입 차단이 풀릴 수 있다. 사용자가 결과 확인 후에만 거래를 원하면 먼저 기존 신규 진입 일시정지를 사용해야 한다. 정지된 엔진이나 사용자가 일시정지한 엔진을 이 작업이 시작/해제하지 않는다.

작업 완료는 계좌 PnL 전체 확인 또는 전략 수익성 승인과 다르다. `account_pnl_verified` / `resume_authorized`를 이 기능만으로 true로 만들지 않는다. 계좌 인증·일일 손실·전략 검증 등 기존 정책은 그대로다.

백업은 계정 DB 옆 `backups/record_recovery/<venue>-before.sqlite3`의 최초 기준본이며 이후 점검이 덮어쓰지 않는다. `record_recovery.sqlite3`에는 작업별 before/after가 남는다. 나중 거래를 잃을 수 있으므로 사용자가 원본 DB 위에 백업을 무조건 덮어쓰는 복구 안내는 하지 않는다.

## 배포 전 남은 필수 작업

1. 계좌별 일별 공식 income/체결/수수료/펀딩/입출금 원장의 누락 없는 수집과 대조. 커서/페이지/시간대/통화/계좌 식별을 증명한다. 잔고 한 장으로 완료하지 않는다.
2. 과거 전략 귀속 미확정과 현재 계좌 위험 미확정을 분리한 재개 조건. 표본 삭제/숨김/cold-start 재분류 금지. 기존 손실·위험 기준 유지와 사용자 재개 의사를 검증한다.
3. 공식 내역 파일 가져오기, provenance와 스키마/기간/계좌 검증. 파일이 있어도 소유권 증거 없는 거래는 성과 인증에 쓰지 않는다.
4. 기관별 historical endpoint/cursor/fee/tax/contract-size/partial-lot 구현과 실제 계좌 검증. 소스 테스트만으로 증권 E2E나 향후 무결함을 보증하지 않는다.
5. 작업 중 보호/청산 지연, API 키 변경/계좌 교체, 네트워크 장기 장애, Windows 설치본 백업/재시작/업데이트를 실제 환경에서 확인한다.

## 고객 데이터 추가 인수 검사 (2026-09-20)

`scripts/verify_customer_record_recovery.py`로 공유 DB 복사본과 실제 로그 64개를 검증했다. 최근 300건의 미대조 40건을 정책 평가에서 재현했고, 모두 유지관리 대상으로 포함됐다. 저장 체결 771건 replay에서는 과거 94건 진입 비용만 보완됐으며 확정 손익 복구는 0건이다. 문제의 40건은 실행 후에도 그대로 차단된다. 로그에서 찾은 통계 commit 후 미정의 ID 반환은 수정했으나 이는 청산 근거 복구와 별개다. 현재 고객 데이터의 최종 복구/재개 인수 조건은 미충족이다. 상세 수치·명령·원본 보존 근거는 [검증 보고](../reports/v39143-record-recovery-verification.md#2026-09-20-고객-db실제-로그-재검증)를 따른다.

## 고객 전체 DB 통합시험

추가 검증: `scripts/verify_customer_history_pipeline.py`는 고객 전체 DB 사본에 시험용 provider 응답만 공급해 실제 worker/native 읽기 어댑터/통계 조회/정책을 검사한다. 첫 1건·2건·40건 합산, timeout·지연 정산·115회 worker 재개·재실행 중복 방지를 통과했다. 40건 복구 후 실제 최근 300건 조회의 미대조 사유는 해소되고 기존 수익성 기준은 유지된다. 이는 고객 실제 API를 받아 정산한 결과와 구분한다. [상세 시험 입력과 결과](../reports/v39143-record-recovery-verification.md#고객-전체-db를-사용한-복구-통합시험-추가)를 참조한다.

## 공식 API 근거

후속 확인: 동일 페이지의 `Query All Algo Orders`와 [Get Income History](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/account#get-income-history). `userTrades`는 주문 ID 없이 날짜·종목으로 조회할 수 있다. fromId와 시간 범위는 함께 보내지 않으므로 포화 구간을 시간으로 나눠 조회한다. income의 전체 계좌 일별 요약과 전략 귀속은 동일하지 않다.

[Binance USD-M Account Trade List](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/trade#account-trade-list-user_data): symbol 필수, 날짜 미지정 최근7일, 요청 기간 최대7일, 최근3개월 제공, limit 최대1000. 실제 코드의 날짜 지정 누락을 보강한 근거이며 다른 기관의 지원 범위를 추정하는 데 사용하지 않는다.
