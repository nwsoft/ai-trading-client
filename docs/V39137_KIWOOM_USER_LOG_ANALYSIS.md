## 확인된 관측

호스트 이벤트는 UTC(+00:00), 거래 로그는 스크린샷과 일치하는 KST로 대조했습니다. 호스트 로그에는 버전 필드가 없으므로 이전/36 구간 분리는 사용자 스크린샷·시간대 기준이며 각 PID의 바이너리 버전을 확정한 것은 아닙니다.

- 19:04~19:30 KST: 14개 호스트 PID. 종목 정보/시세 조회 이후 새 PID가 등장하거나 로그인 단계에서 진행이 중단됩니다. 여러 구간에서 마지막 조회 후 다음 호스트 시작까지 약 35초입니다. 서버/인터넷 장애의 직접 증거는 없습니다.
- 21:37:22.964: PID 25940 시작. 21:37:23경 connect/ActiveX 초기화 이후 잔고·포지션·미체결·종목 목록 조회 단계로 진행합니다.
- 21:37:31.277~31.357: get_stock_info→get_realtime_price→is_etf→get_stock_info. 해당 PID의 마지막 이벤트는 **21:37:31.357 get_stock_info**입니다. 완료 이벤트가 없던 구버전 로그이므로 OCX 내부의 정확한 중단 지점은 알 수 없습니다.
- 21:38:04: 거래 로그는 PAPER 주기 완료·주문 0건을 출력합니다. 조회 시점 약 33초 후이며 RPC 기본 제한 30초+종료 대기 3초와 부합합니다. 이는 코드와 시간의 대조 추론이지 TR 오류 코드 확인은 아닙니다.
- 21:39:04: 자동 재로그인 차단. 이것은 앞선 실패의 후속 안전 상태입니다. 최초 오류 메시지가 거래 로그에는 보존되지 않았습니다.
- 21:41:31: 워커 중지. 21:41:34 새 PID 30292 시작 후 잔고/포지션/미체결 단계가 23:38까지 반복됩니다. 종목 분석·PAPER 회복이나 계좌 데이터 정상 수신 증거로 간주하지 않습니다.

## 코드에서 확인한 결함 / 37 수정

1. pykiwoom 동기 TR의 무제한 이벤트 대기, 즉시 반환 코드 유실: 호스트 내부 제한·요청 간격·콜백 상관관계·오류 코드 판별을 추가했습니다. -200 이후 보류는 RPC 제한시간 동안 잠들지 않고 빠르게 오류를 반환합니다.
2. 종목 분석의 metadata/quote 중복 opt10001: 1초 이내 성공 응답 공유. 실패/만료 응답은 재사용하지 않습니다.
3. 종목명만 확보돼도 TR 실패를 삼키고 status=ok: 오류 반환으로 수정. 공통 증권 분석은 명시적 조회 오류를 점수·신규 진입에 사용하지 않습니다.
4. pykiwoom 실제 목록 반환과 어댑터 문자열 가정, 잔고/보유종목/미체결 output 및 ETF/거래내역 TR 계약: 계약을 바로잡았습니다. 로그인 비밀번호를 계좌 조회 비밀번호로 전송하지 않습니다.
5. 원인 소실: RPC 완료·TR 제출/콜백/완료/거부·호스트 버전 기록, 수동 재연결 문구에 최초 원인 보존. 부모의 통신 실패도 자식 전용 환경변수 없이 기록합니다.
6. 여러 TR의 누적 대기가 부모 제한을 넘는 경로: RPC별 공통 대기 예산을 적용했습니다. 분석 오류가 있는 주기는 경고로 표시하고 최초 오류를 유지합니다.

PyPI 배포본 pykiwoom **0.1.6**의 소스에서도 TR 무제한 대기 구현을 직접 대조했습니다. 최종 자동 검증은 전체 **2,491 passed / 8 skipped / 3 subtests passed**, 집중 **135 passed / 3 subtests passed**입니다. Windows 실제 재현 결과가 아닙니다.
