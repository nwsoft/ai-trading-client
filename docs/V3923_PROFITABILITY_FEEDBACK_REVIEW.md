## 2. 고객이 지금 취할 수 있는 조치

1. **설치 버전·UI 버전, Binance의 실제 운용 모드, 로그 시각을 확인한다.** 고객이 어떤 업데이트를 설치했는지 스크린샷만으로 추정하지 않는다.
2. 거래 통계에서 해당 거래소·기간·실거래/가상거래 범위와 수수료 차감 손익을 확인한다. 통계 값과 게이트 표본이 동일하다고 전제하지 않는다. 지원 담당자가 적용 정책의 `underperformance_mode`, 일반/Hard MDD 기준, 실제 평가값·표본·제외행을 함께 대조한다. 현재 UI에서 이 전체 보고서를 볼 수 있다고 안내하지 않는다.
3. 현재처럼 미대조 0이고 reason이 성과 미달이면 기록 복구/초기화가 해결책이라고 안내하지 않는다. 별도로 `pnl_reconciliation_required`가 있거나 실제 미대조 기록이 보일 때만 **설정 → 업데이트 → 유지관리 → 거래 기록 점검·복구**로 진행한다.
4. `strict_stop`이 의도한 설정이고 올바른 표본으로 성과가 미달했다면 보류가 정책대로다. 정책을 자동 완화하지 않는다. `limited_learning`이 적용돼야 하는데 strict로 해석됐다면 설정 병합/전달 문제를 수정할 대상이다. Hard MDD를 넘었거나 평가 근거가 불충분하면 회복 운용으로 통과시키지 않는다.
5. 재시작 반복·전체 가드 OFF·승률/MDD 기준 완화·성과 초기화·전략 전환을 고객 해결 절차로 제시하지 않는다. PAPER 전환만으로 이 게이트가 풀린다고 약속하지 않는다. 현행 후보 차단은 PAPER 경로에도 영향을 줄 수 있고 평가 표본은 LIVE에서 읽는 경로가 있기 때문이다.

고객 전달 문안:

> 보내주신 화면에서는 Binance의 시장 분석은 진행되고 있지만, 기존 성과를 검사하는 단계에서 기본 전략의 신규 진입이 보류되고 있습니다. 표시된 0/300은 거래가 0건이라는 뜻이 아니라 조회한 표본 중 미대조로 표시된 건수가 0이라는 뜻입니다. 현재 화면에는 적용 정책과 실제 낙폭이 없어 정상적인 손실 보호인지 설정 적용 문제인지 확인이 필요합니다. 설치 버전·PAPER/LIVE와 해당 시각의 진단 기록을 대조하겠습니다. 그동안 거래를 열기 위해 기록을 초기화하거나 보호 기준을 끄지는 마세요.

### 3.1 재현 수치

- 합성 300행: `i % 11 < 3`이면 수익률 +0.001, 아니면 -0.0021, 금액은 각각 +0.1/-0.21, `performance_evidence_ready=true`. 승률 0.28, MDD 0.3135, 첨부와 같은 5개 미달 reason이 발생했다. **고객 승률/MDD가 아니다.**
- 위 표본 + 온전한 템플릿: `recovery_learning`, enabled true, 위험배수 0.20. 같은 표본 + strict 또는 Binance/Bybit 부분 override: enabled false. 동일 reason 목록만으로 Hard stop 여부를 구분할 수 없다.
- 시간순 20건 +2%, 이후 20건 -2%: 최근 기대값 -0.02, 회복배수 0.15. 같은 행을 역순으로 주면 최근 기대값 +0.02, 회복배수 0.20. Binance 표본 메서드 가짜 Recorder 확인에서도 `[최신, 과거]` 순서를 유지했다.
- 1건 -50%: MDD 0.5인데 cold start 경로가 enabled true. 금액만 있는 30행: excluded 30, 유효표본 0인데 cold start enabled true.

이 결과를 근거로 정책을 일괄 `limited_learning`으로 바꾸는 것은 수정안이 아니다. 사용자가 선택한 strict 유지, 중첩 정책 상속의 일관성, 신뢰 가능한 표본, Hard stop 우선순위가 함께 필요하다.

## 4. 수정 계약과 사용자 화면 요구

### 4.1 정책·표본·판정

- `공통 기본 → 저장한 사용자 정책 → 거래소/증권사 override`를 필드별로 합성하고 각 값의 출처와 유효값을 남긴다. 생략과 명시 null/false/0의 의미, 잘못된 값의 거부, legacy migration을 정의한다. 명시 strict를 자동 회복 모드로 바꾸지 않는다.
- 최신 기간/개수를 **UTC로 정규화한 종료시각+안정된 tie-breaker**로 선택한 뒤 평가에는 과거→최신순을 사용한다. 기간 필터·동일시각·중복·partial close·시간대·수정된 기록의 재계산을 시험한다.
- 원장 읽기 실패·미대조·비유한/불명 수익률·원금 없음·비용 누락을 진짜 0거래와 구분한다. 지표 단위/순손익/비용 차감 횟수·통화를 검증하고, 미확인을 0이나 정상으로 만들지 않는다.
- 실제 계좌 equity MDD와 거래별 수익률을 복리로 연결한 지표를 서로 다른 이름/기준으로 표시한다. 레버리지·투입원금·부분청산·동시 포지션의 의미를 검토한다. 현재 거래별 지표를 계좌 손실률이라고 재명명하지 않는다.
- 데이터 신뢰/Hard stop/일일·계좌 보호와 cold start·일반 성과회복의 우선순위를 명시한다. 최소 표본 미달이 확인된 큰 손실을 덮으면 안 된다. 숫자 경계·표본 제외·재시작에서도 같은 판정을 내야 한다.
- 기본/confirm/독립 전략은 해당 성과 귀속과 기존 후보 정책을 보존한다. 독립 전략을 선택해서 계좌 공통 손실·권한·보호 가드를 우회하지 않는다. 모든 전략의 손익을 기본 전략의 단일 성과로 잘못 합산하는지도 점검한다.
- LEARNING 판단 기록, PAPER 종료 거래, LIVE 종료 거래의 저장소와 용도를 분리한다. PAPER 검증을 위한 명시적 안전 경로를 만들되 PAPER 양호를 LIVE 자동 승인으로 바꾸지 않는다. 기존 보유 관리·TP/SL은 신규 진입 보류 중에도 살아 있어야 한다.

### 4.2 고객이 해결 가능한 진단 화면

거래소의 보류 메시지에서 `차단 근거 보기`를 열어 다음을 보여주는 것을 P0 요구로 둔다. 현재 제공 완료 화면이 아니다.

1. **상태:** 성과 미달(strict), 일반 회복, Hard stop, 표본 부족, 기록 미대조, 정책 오류, 지표 계산 불가, 시세/권한 차단을 구분.
2. **현재 판단:** 기관/운용 모드/전략·버전/시점/샘플 범위·원시/유효/제외/미대조 수, 각 지표의 실제 값·기준·단위·근거.
3. **적용 정책:** 공통/기관 override·선택 모드, 위험배수·최대 포지션/레버리지와 계좌 상한. 사용자가 설정한 값과 실제 적용값의 차이.
4. **다음 행동:** 원인별 거래기록 대조·설정 확인·전략 검토·격리 PAPER 검증·데이터 새로고침·진단 내보내기. 실행 가능한 버튼만 표시하며 권한/위험 설정 변경은 미리보기와 명시 저장을 거침.
5. **재평가:** 무엇이 바뀌면 다시 계산하는지, 마지막/다음 확인·진행을 표시. 같은 자료를 계속 읽으며 표본 축적 중이라고 하지 않음.
6. **로그/AI:** 같은 상태는 요약/주기 제한, 상태/값/정책 변경은 즉시 기록. AI는 해당 진단 snapshot의 값만 인용하고 실값이 없으면 요청한다. “끄세요/완화하세요”를 기본 답변으로 하지 않음.

## 7. 추가 피드백: 거래소 공통 범위와 패치를 기다리지 않는 복구

사용자 문제 제기: 차단 뒤 대응 기능이 없으면 고객은 이용을 중단한다. 비슷한 문제가 생길 때마다 다음 기능 업데이트까지 기다리는 운영은 받아들일 수 없다. **원인별 앱 내 복구·재검증·재개와 긴급 수정의 별도 전달 경로**를 필수 요구로 둔다.

### 7.1 영향 범위와 현재 복구 기능의 실제 한계

| 항목 | 확인된 범위 | 해석 |
|---|---|---|
| 정책 부분 override의 중첩값 소실 | Binance 전용/UnifiedTrader 공통 코인 메서드, Binance·Bybit 합성 재현 | 다른 코인 거래소에도 같은 조건에서 가능. 모든 거래소/고객에게 이미 발생했다는 뜻은 아님 |
| 소표본/불명 근거의 cold start 분기 | 공통 ProfitabilityValidator; Binance·공통 코인·StockAnalysisService가 사용 | 거래소 장애가 아니라 클라이언트 공통 로직 문제. 각 어댑터의 입력 계약/추가 가드에 따라 최종 영향 다름 |

이번 문제는 **① 정상적인 성과 보호 ② 정책 상속/평가 데이터 처리 결함 ③ 사용자가 구분하고 복구할 수 없는 안내/도구 부족**이 섞인 것이다. 공통 오류와 사용자가 의도한 차단을 같은 원클릭 우회로 풀지 않는다.

### 7.2 현재 고객의 대응과 긴급 수정 순서

1. 설치본/모드·실효 정책·평가 표본/값을 진단해 이번 고객의 원인을 확정한다. 앞서 질문한 정보는 아직 미확보다. 이를 다시 받기 전 전체 초기화나 거래소 변경을 고객에게 시키지 않는다.
2. **설정 저장 오류로 확인되면:** 현재 설치본이 읽을 수 있는 범위에서 원래 의도한 항목만 백업→변경 미리보기→명시 확인→대상 기관 재평가로 교정하는 지원 절차를 검토한다. 기존 버전에서 가능한지는 실제 설정/버전으로 검증한다. 의도한 strict를 임의로 limited로 바꾸는 작업은 복구로 가장하지 않는다.
3. **확인된 원장 문제면:** 기존 거래 기록 복구 경로를 사용하고, 완료 후 새 근거로 재평가한다. 자료 미확정은 실패 이유와 추가 확인을 표시한다.
4. **현재 설치 코드의 계산/상속 결함이면:** 설정 초기화로 코드가 고쳐지지 않는다. 재현→좁은 수정→영향 경로 회귀→Windows 설치/업그레이드·보호관리→고객 재현 순으로 **긴급 안정화 수정분을 우선 전달**한다. 생활금융 기관 계약/전체 기능 완료까지 묶어 기다리게 하지 않는다. 버전 번호/게시 일정은 산출물과 인수에 맞춰 확정하며 여기서 새 공개 버전을 임의 지정하지 않는다.
5. 진단 전에도 보유 관리/보호 상태와 다른 기관의 상태는 개별 확인한다. 한 기관의 복구 때문에 전체 기관을 재시작하거나 무관한 정상 거래를 중단하지 않는 것을 제품 계약으로 삼는다. 현 설치본이 이를 모두 만족하는지는 별도 인수다.

현재 화면만으로 고객에게 “이 버튼을 누르면 바로 정상 거래된다”고 보장할 근거는 없다. 이 한계를 명확히 알리되 기본 지원 절차를 “다음 버전을 기다리세요”로 끝내지 않는다. 진단 결과·현 버전 조치 가능 여부·긴급 수정 필요 여부·담당/진행을 같은 사건 ID에서 추적한다.

### 7.4 공통 복구 상태와 재발 방지 계약 (추가 RECOVERY23-01~04)

목표 흐름: `문제 감지 → 보유 보호 상태 확인·신규 진입 범위 제한 → 원인 진단 → 적용 가능한 복구 제안 → 수행/확인 → 새 근거로 재평가 → 정상/제한 검증/보류 사유 표시`.

- **RECOVERY23-01 진단/복구 등록부:** 시세/연결·후보 데이터·계정 권한·정책 상속·성과 미달·Hard stop·기록 미대조·주문 상태 불명을 서로 다른 코드로 관리한다. 각 코드에 필요한 근거, 사용자 설명, 허용 동작, 재개 조건, 자동/확인/지원 담당 범위를 등록한다. 새로운 reason이 등록되지 않았으면 unknown으로 남기며 엉뚱한 복구를 실행하지 않는다.
- **RECOVERY23-02 제한 재시도·선택 복구:** 조회/캐시 갱신처럼 승인 범위 내의 읽기 작업은 자동 재시도·backoff·시도 한도·취소를 제공한다. 설정/원장 변경은 diff/명시 확인과 계정/기관/버전 잠금을 거친다. stale 진단에 기반한 변경과 동시 중복 복구를 차단한다. 결과가 불명인 주문은 상태를 먼저 조회하고 신규 주문을 중복 전송하지 않는다.
- **RECOVERY23-03 재개 계약:** 일반 장애에서 일시 보류한 기관은 기존 운용 권한 안에서 정상화/재평가 후 복귀할 수 있다. 사용자 명시 정지, 계정 권한 철회, Hard stop, 새 위험 정책 동의가 필요한 상태는 자동 LIVE 재개하지 않는다. UI는 자동 복귀 가능 여부와 조건을 사전에 보여준다. PAPER 검증이 LIVE로 자동 승격되지 않는다.
- **RECOVERY23-04 운영/전달:** 반복 횟수·경과·다음 시도·상태 변화·마지막 정상·실제 복구 결과·진단 내보내기를 제공한다. 자동 해결되지 않으면 같은 경고만 쌓지 말고 해당 원인/다음 조치를 표시한다. 코드 결함의 긴급 수정은 생활금융 기능 릴리스와 분리해 인수/배포 가능하게 관리한다. 서버에서 거래 실행 코드를 임의 교체하거나 원격으로 보호 기준을 끄는 방식은 사용하지 않는다.
